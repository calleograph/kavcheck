## [0.9.5] — 2026-10-27

### EOL: устойчивая запись на нескольких источниках и диагностика

- **Запись результатов не падает на повторах ключа.** Одинаковые находки объединяются до записи (разные факты — другой регистр, пробел, версия — остаются отдельными), запись идёт пакетами с разрешением конфликта обновлением и одной транзакцией под блокировкой источника: ни одна находка не теряется, прежний результат при ошибке цел, источники независимы.
- **Понятные ошибки.** Пользователь видит «Не удалось рассчитать EOL для источника. Обнаружен конфликт данных при сохранении результатов. Предыдущие результаты сохранены.» вместо текста SQLAlchemy; администратор — этап, операцию и конфликтующий ключ (под сообщением на странице EOL и в журнале событий). Расчёт, отложенный из-за нехватки памяти, теперь тоже виден как состояние, а не молча оставляет прежнюю ошибку.
- **«Все источники»:** итоги по рассчитанным источникам, неполнота названа явно («Данные неполные: нет результата по …»), в зонах числа EOL — только по рассчитанным источникам с пояснением.
- **Диагностика только для чтения:** `python -m app.tools.eol_diag` — состояние расчёта по источникам, давность ошибки (старая или свежая), причина, по которой расчёт не запускается, повторы версий в каталоге, ключи к объединению (docs/EOL.md, docs/VERIFY_REAL_SOURCES.md). Миграция 0014.
- Установленная причина ошибки на конкретном источнике по данным разработки не подтверждена (рабочих баз нет): в коде не найдено пути получить повтор ключа внутри одного расчёта даже на данных с экзотическими строками; вероятные причины — расчёт без блокировки в старой версии, прерванный расчёт крупного источника (память) с оставшейся прежней ошибкой, чужая параллельная запись. Теперь любая из них либо разрешается без потери данных, либо называется в диагностике.

## [0.9.4] — 2026-10-26

### Контроль ресурсов Linux: исправление порогов

- В 0.9.3 по ошибке была снижена норма ядер CPU (с 3 до 2) — возвращена: 3 ядра и больше — норма, 2 — предупреждение, 1 — критично.
- Порог ОЗУ снижен с 2048 до 1792 МБ: сервер «с 2 ГБ» (в KSC он часто виден как 1,9 ГБ) больше не получает предупреждение «Недостаточно ОЗУ». Порог настраивается: «Администрирование → EOL и пользователи → Ресурсы Linux-серверов»; если вы сохраняли значения вручную, они остаются прежними.

## [0.9.3] — 2026-10-26

### Исправления после проверки 0.9.2 на рабочей инфраструктуре

- **EOL: расчёт падал с `duplicate key value violates unique constraint "eol_findings_pkey"` — исправлено.** Причина: каталог хранит одну и ту же версию продукта несколько раз (по схеме версий и платформе), из каждой записи получалась своя находка с одним ключом; ту же ошибку давали два одновременных расчёта одного источника (воспроизведено тестами на PostgreSQL). Теперь версии объединяются, замена результатов идёт под блокировкой источника и одной транзакцией, прежний результат не теряется при ошибке.
- **EOL: понятные состояния** — «Не рассчитано», «Выполняется» (с этапом), «Ошибка», «Готово», «Данные устарели». Пока результата нет, вместо нулей показывается «—» с объяснением, а в зонах скрывается колонка EOL. Прерванные падением worker расчёты сбрасываются при запуске.
- **Отчёты: ошибка «Input should be a valid string» (`params.zone = null`) — исправлено** во всём конструкторе: необязательное поле со значением `null` получает значение по умолчанию (зона не выбрана — проверка по всем компьютерам). Ошибки проверки параметров теперь по-русски и с названием поля, а не сырой список.
- **Отчёты: память и надёжность.** XLSX пишется потоком: отчёт на 100 тыс. строк занимал около 1 ГБ памяти worker, теперь около 230 МБ. Повторная отправка того же отчёта не создаёт второе задание; лишние задания ждут «в очереди», а не «в работе»; при временной недоступности источника отчёт повторяется (30 с, 2 мин).
- **Карточка компьютера: уязвимости по продуктам.** Одна строка на установленный продукт и версию (критичность, уникальные CVE, KEV, EOL, три идентификатора и «+N»); полный список раскрывается по нажатию и подгружается с сервера страницами. Счётчики не сокращаются.
- **База уязвимостей: план устранения.** Показатели с раздельными единицами (уникальные уязвимости, продукты; компьютеры — только по версиям каталога и при проверке), вид «План устранения: по продуктам» (что обновить, затронутые версии, компьютеры ≈, KEV, EOL), категории продуктов (операционные системы, системные компоненты, прикладное ПО, не классифицировано) с ручным назначением, фильтры по достоверности сопоставления, KEV, EOL, критичности. Подробно и аудит цифр — [docs/VULNDB.md](docs/VULNDB.md). Миграция 0013.
- **Скорость страниц.** Страницы «Состояние защиты» и «Уязвимости» и главная сразу показывают прежние данные (с временем получения) и обновляются в фоне (`CACHE_SWR_SECONDS`); список уязвимостей KSC читает два независимых агрегата параллельно.
- **PostgreSQL и контейнеры.** Настройки PostgreSQL под нагрузку (раньше — значения по умолчанию: 128 МБ буферов), лимит памяти базы, отдельные тайм-ауты worker (длинные расчёты не обрываются на 2 минутах страниц), закрытие транзакций «в простое», проверка работоспособности worker, `oom_score_adj` worker (при нехватке памяти первым завершается он, а не база), `init`. Миграция 0012.
- **Наблюдаемость.** «Состояние системы → Фоновые расчёты»: память worker (текущая, пик, пределы), что выполняется, по каждому источнику — время, длительность и ошибки расчётов EOL, зон, пользователей, каталога; длительность отчётов; долгие транзакции PostgreSQL.
- **Контроль ресурсов Linux:** норма по ядрам CPU снижена с 3 до 2 (1 ядро — по-прежнему критично); при норме 2 предупреждения «Мало ядер CPU» нет. Порог настраивается: «Администрирование → EOL и пользователи → Ресурсы Linux-серверов».
- Известное ограничение: страницы «Состояние защиты» и «Уязвимости» по-прежнему читают KSC напрямую; на источниках свыше 200 тыс. устройств им нужен перенос на подготовленные данные (docs/PERFORMANCE.md).

## [0.9.2] — 2026-10-26

### Аппаратные характеристики и контроль ресурсов Linux-серверов

- **Карточка компьютера:** новая вкладка «Аппаратная часть» (последняя): процессоры и ядра, ОЗУ, диски — физические и логические отдельно, общий и свободный объём, сеть, плата; для виртуальных машин — выделенные ресурсы. В «Сведениях» — компактная строка «Диски: 120 ГБ · CPU: 2 ядра · ОЗУ: 4 ГБ»; нет данных — «Нет данных».
- **Контроль ресурсов только для Linux-серверов** (Windows и рабочие станции не затрагиваются): 3 ядра и больше — норма, 2 — предупреждение «Мало ядер CPU», 1 — критическая «Недостаточно ядер CPU»; «Недостаточно ОЗУ» — меньше настраиваемого порога (по умолчанию 2048 МБ). В проблеме — фактическое значение и порог.
- **Где видно:** «Состояние защиты» (фильтр «Аппаратные ресурсы» и по критичности, сводка с порогами), зоны ответственности (свои серверы с нехваткой ресурсов, переход в карточку, отчёты и рассылки зон), плитка на дашборде. Отдельный тип проблем: в счётчики CVE и EOL не входит.
- **Настройки:** «Администрирование → EOL и пользователи → Ресурсы Linux-серверов» — включение, пороги, исключения по маскам. Данные берутся из инвентаризации KSC (только чтение); нет данных — оценка пропускается. Подробно: [docs/HARDWARE.md](docs/HARDWARE.md). Миграция 0011.

## [0.9.1] — 2026-10-26

### Уязвимости компьютера, программы и проверка инфраструктуры

- **Карточка компьютера:** вкладка «Уязвимости» теперь показывает **все** уязвимости в одном списке — подтверждённые KSC и найденные по внешним базам (NVD, CISA KEV, OSV, БДУ). Раньше внешние базы были на отдельной вкладке, и при «Уязвимости 0» по KSC создавалось ложное впечатление, что проблем нет. Вкладка «Внешние базы» объединена с ней (старые ссылки открывают общий список).
- В строке: CVE (ссылка на запись в базе уязвимостей), программа и установленная версия, критичность, **источник обнаружения** (KSC, базы), **статус проверки** («Подтверждено KSC», «Подтверждено внешней базой», «Потенциальная»), ссылка на описание KSC. Уязвимость, найденная обоими источниками, — **одна строка** с обоими источниками (совпадение по идентификатору и версии). Счётчик на вкладке учитывает все результаты; фильтр различает «подтверждены KSC» и «только внешние базы». Данные KSC показываются сразу, проверка по внешним базам (дольше) подгружается следом и кэшируется; недоступность одного источника не скрывает другой.
- **Программы:** в карточке продукта кнопка «Где установлено» (рядом с «Проверить версии» и в блоке «Известные уязвимости») открывает список компьютеров со всеми версиями; имена — ссылки на карточки.
- **Проверка инфраструктуры** (кнопки «Проверить» в «Базе уязвимостей» и у продуктов): над результатами — компактная строка затронутых компьютеров со ссылками, длинная сворачивается («Показать все»).
- **Меню пользователя:** внизу — ссылки на GitHub проекта, автора (calleograph), номер версии и список изменений (на тег текущей версии).
- Исправлено: в репозиторий 0.9.0 по ошибке попала символическая ссылка `backend/.venv`; удалена, `.gitignore` теперь игнорирует `.venv` и как ссылку.

## [0.9.0] — 2026-10-26

### EOL: жизненный цикл программ и ОС

- **Новый раздел «EOL»** ([docs/EOL.md](docs/EOL.md)): какие программы и ОС вышли из поддержки производителя или выйдут в ближайшее время. Сроки — из открытой базы endoflife.date (API v1, источник подсистемы баз уязвимостей: условный запрос по ETag, записываются только изменившиеся продукты, по расписанию и вручную; при недоступности сайта остаётся прежняя копия).
- **Достоверность.** «EOL» присваивается, только когда закончилась стандартная поддержка безопасности; расширенная (платная, по договору) поддержка показывается отдельно и не считается подтверждённой; нет дат — нет EOL; ветка выбирается по установленной версии (`PHP 7.4.16 → 7.4`), ОС — по сборке и редакции Windows, номеру выпуска Ubuntu, Debian, RHEL и клонов; неоднозначные соответствия не угадываются. Ручные соответствия («эта программа = этот продукт», «не проверять EOL») сохраняются при обновлении базы и каталога.
- **Что видно:** таблица программ и ОС с критичностью, состоянием поддержки, датами (стандартная и расширенная — раздельно), числом устройств и списком устройств с переходом в карточку; все продукты базы со сроками веток; фильтры по типу, состоянию, критичности, производителю, продукту, источнику и зоне; выгрузка Excel/HTML/CSV через конструктор отчётов (`quick_eol`, список устройств — полный).
- **EOL — отдельный тип в общем списке проблем:** переключатель «Все / CVE / EOL» в «Уязвимости» и «База уязвимостей», отдельные счётчики «устройств с EOL» в дашбордах и списке зон (устройство считается один раз), блок EOL в карточке компьютера. «Администрирование → EOL и пользователи» отключает EOL в общей аналитике.
- Расчёт — в worker под общим ограничителем ресурсов, порциями; страницы читают готовые таблицы (`eol_findings`, `eol_hosts`) и KSC не опрашивают. Пересчёт запускается сам при изменении базы EOL, этапов поддержки веток, каталога и решений; при ошибке остаются прежние результаты.

### Устройства и пользователи

- **Новый раздел «Устройства и пользователи»** ([docs/DEVICES.md](docs/DEVICES.md)): имя, IP, ОС, источник, группа, зоны, последнее подключение к KSC, пользователи и число проблем EOL — одной таблицей, карточка устройства.
- **Честно о пользователях.** KSC 15.1 хранит только списки «вошли сейчас» и «входили ранее» без дат входа; «последнего пользователя» в нём нет. KAV Checker опрашивает списки по расписанию (по умолчанию раз в час, лёгкая выборка порциями) и накапливает наблюдения: «сейчас», «последний замеченный в сеансе» (дата наблюдения, а не время входа), «за 7 суток» (замеченные в сеансе или впервые появившиеся после начала наблюдений), «входили ранее» (без дат). Служебные и системные учётные записи скрыты (маски настраиваются). Ограничения описаны в документации и в интерфейсе.
- **Единый поиск** по имени, FQDN, IP и логину ([docs/DEVICES.md](docs/DEVICES.md)): маски `*`, несколько значений через пробел или запятую, адрес, сеть CIDR, диапазон, маска по октетам; адреса ищутся по числовому диапазону (быстро на сотнях тысяч устройств), значения передаются только параметрами SQL. Работает в «Устройствах и пользователях», «Компьютерах» и таблицах зон.
- **«Все источники»** в выборе источника: все доступные пользователю источники, включая добавленные позже; права не обходятся; у каждой записи указан источник; недоступный источник помечается предупреждением. Работает в «EOL», «Устройствах и пользователях», «Отчётах»; остальные разделы показывают выбранный источник (об этом сообщает заметка вверху страницы).
- **Компактные списки:** в ячейках таблиц не больше трёх значений и «+N», по нажатию — полный список; в выгрузках списки всегда полные.

## [0.8.0] — 2026-10-26

### Критическая ошибка: фоновая служба занимала всю память сервера

- **Причины** (воспроизведены на стенде: 6,8 ГиБ у worker; подробности и измерения — [docs/PERFORMANCE.md](docs/PERFORMANCE.md)):
  1. **Анализ уязвимостей по каталогу** (`vdb/sync.analyze`) загружал в память *все* записи затронутых продуктов всех подходящих уязвимостей как объекты ORM и держал транзакцию открытой на время вычислений — отсюда `idle in transaction` по `vdb_affected` и тайм-ауты. Он запускался при каждом старте worker для каждого источника, поэтому после обновления и перезагрузки память росла за минуты (≈60 КБ на находку: ~7 ГБ при ~100 тыс. находок).
  2. **Преобразование оценок CVSS при старте** (`upgrade_scores`) читало все записи базы уязвимостей в одной сессии: объекты копились в памяти.
  3. **Кэш данных зон в памяти** (0.7.0): наборы всех компьютеров и обнаружений источника и индекс совпадений с внешними базами (для компьютера — тысячи «потенциальных» строк) держались в процессе worker.
- **Исправлено в алгоритмах**, а не лимитами: анализ читает строки порциями по 300 уязвимостей без ORM и фиксирует результат после каждой порции (пик +35 МБ вместо +440 МБ на том же наборе, результат тот же; прерванный пересчёт продолжается); преобразование оценок читает только нуждающиеся записи и сбрасывает сессию; решения администратора пересчитывают только затронутые уязвимости; карточка компьютера в разделе «База уязвимостей» читает порциями.
- **Ограничитель ресурсов worker** (`services/resources.py`): анализ уязвимостей, сборка каталога, расчёт зон и отчёты идут по одной тяжёлой задаче (настройка), отчёты пользователей — на отдельном месте, чтобы ночной расчёт их не задерживал. Мягкий предел памяти (50 % лимита контейнера) откладывает новые задачи, жёсткий (75 %) останавливает текущую на границе порции: она повторяется без потери данных. Контейнеры: `WORKER_MEM_LIMIT` (3 ГБ по умолчанию, без swap) и `BACKEND_MEM_LIMIT` (1 ГБ), `MALLOC_ARENA_MAX=2`. Пик памяти виден в «Администрирование → Расчёт данных зон».

### Подготовленные данные зон: ночной расчёт и мгновенное открытие

- Страницы зон, фильтр «Зона» в разделах и отчёты **читают готовые данные из PostgreSQL** и не обращаются к KSC при открытии. Расчёт — в worker, **по одному источнику, порциями** (компьютеры, поток обнаружений KSC, потенциальные совпадения из компактного индекса версий каталога), результат подменяется одной транзакцией; ошибка оставляет прежние данные с отметкой возраста и причиной. ### Помощник обновлений: исправление повторяющегося сбоя (аудит)

- **Причина.** Обновление исполняло скрипты *установленной* версии: до 0.6.x это `update.sh` с выбором «сборка по `IMAGE_REPO`» (поэтому образы ghcr игнорировались и запускались `npm ci`), а помощник обновлял пульс только на строках `[N/M]` — во время `docker compose build` пульс замирал, и интерфейс писал «помощник не запущен» при идущем обновлении. Исправления нового релиза не могли повлиять на обновление, которое выполняется старым кодом.
- `update.sh` стал пусковой частью: распаковывает скрипты целевого релиза из git и выполняет `update-core.sh` оттуда; версия «работает сейчас» берётся из приложения, а не из файла `VERSION`.
- Пульс (`heartbeat.json`) пишет отдельный процесс, независимый от операции; операция (`operation.json`) имеет идентификатор, фазу и время последнего вывода; процесс операции проверяется по pid. Интерфейс различает «помощник доступен», «операция выполняется» и «прервано», показывает конкретную причину недоступности (остановлена, перезагрузка без запуска, пульс не обновлялся) и результат самодиагностики службы (`updater.sh doctor`).
- Локальная сборка — только явный режим (кнопка, `--build`, `UPDATE_MODE=build`); скрытый переход `UPDATE_ALLOW_BUILD` удалён. При сборке реально проверяются источники зависимостей (скачивание пакетов), поддержаны списки `NPM_REGISTRIES`/`PIP_INDEX_URLS`, попытки ограничены.
- Автоматическое восстановление не запускает прежнюю версию на несовместимой схеме базы; после обновления процесс помощника перезапускается на новом коде. После неудачного обновления код возвращается к состоянию **до** обновления (а не к тегу прежней версии), поэтому свежие скрипты не заменяются устаревшими и повторная попытка не запускает старую логику со сборкой образов (найдено настоящим тестом `real.sh`). Дочерний процесс паузы не удерживает блокировку службы после аварийного завершения помощника (найдено сценарием 26 `run.sh`: перезапуск сразу после аварии мог упереться в «уже запущен»).
- Испытания: `tests/updater/run.sh` (подставной docker) и новый `tests/updater/real.sh` — настоящий Docker и systemd: недоступный реестр, ошибка миграции, «перезагрузка» посреди миграции, повтор без ручных действий, переход с локальных образов на релизные, падение помощника и перезапуск backend, откат на несовместимую схему.

### Обновление: надёжность

- **Обновление идёт из готовых образов (ghcr.io), а не локальной сборкой.** Причина прежнего поведения: выбор «собирать или скачивать» зависел от вида `IMAGE_REPO`, а у установки из исходников он `kavcheck` — любое обновление уходило в сборку, которой нужны Docker Hub, npm и pip. Теперь репозиторий образов определяется по `IMAGE_REGISTRY`/`GITHUB_REPO`/`origin`; локальная сборка — только по кнопке «Собрать локально» (с подтверждением), `--build`, `UPDATE_MODE=build` или `UPDATE_ALLOW_BUILD=1`, всегда с записью в журнал.
- Тайм-ауты и контроль прогресса по этапам (сеть, загрузка образов, сборка, резервная копия, миграции, запуск) и общий сторож помощника: зависшая операция останавливается вместе с дочерними процессами, блокировка снимается, причина записывается.
- Восстановление после перезагрузки или остановки помощника: метка незавершённого обновления, `scripts/recover.sh` при старте помощника и перед ручным обновлением; безопасный возврат по этапу (прежняя версия или проверенная новая), повторное обновление автоматически не запускается; статус «Выполняется» от умершего процесса снимается.
- Диагностика причин: Docker Hub, реестр образов, образов нет, npm, pip, сеть, диск, сборка, миграция, проверка здоровья, тайм-аут, прерывание — с советом в отчёте и интерфейсе. Зеркала npm/pip, настроенные на сервере, сохраняются в `.env`; проверяются фактически используемые источники; кэш npm между сборками.
- Помощник обновлений устанавливается установщиком автоматически (служба systemd с `Restart=always` без предела перезапусков), проверяется `updater.sh verify`, обновляется вместе с релизом и перезапускается на новом коде.
- В разделе «Обновления»: реальный этап, длительность, время последнего вывода, предупреждение о зависании, красная плашка при ошибке с причиной и действиями, **кнопка «Скачать журнал»** последнего обновления для диагностики (секреты маскируются).
- Образы: после успешного обновления остаются текущая и предыдущая версии; копии `.env` — последние 5. Тесты сценариев отказов — `tests/updater/run.sh` (в CI).

### Быстрые контекстные отчёты

- Отчёт из любого раздела за 2–3 действия: отметьте строки флажками (или нажмите «Отчёт по этой уязвимости») → «Сформировать отчёт» → в боковой панели сразу число затронутых компьютеров, условия, замечания о достоверности и первые строки → «Excel», «HTML для руководства» или «CSV». Источник, выбранные записи, поиск, фильтры, давность связи и «только в сети» передаются в отчёт автоматически; дополнительные условия — в раскрывающемся блоке «Дополнительно».
- «Уязвимости»: новая вкладка со списком уязвимостей KSC (KLA, CVE, опасность, программы, число компьютеров, исправление) с поиском по CVE и KLA; отчёт по одной или нескольким уязвимостям. Вкладки «Уязвимые программы» и «Компьютеры» тоже выбирают строки; карточка компьютера уязвимостей и карточка компьютера — «Подробный отчёт».
- «Компьютеры»: отчёт по выбранным устройствам — состояние, защита, установленное ПО, уязвимости (разделы выбираются). «Состояние защиты»: отчёт по текущей категории и фильтрам или по выбранным устройствам. «События безопасности»: отчёт по текущему списку (период, результат, угроза, поиск) или по выбранным событиям. «Каталог программ» и конструктор проверки версий: «Сформировать отчёт» с тем же предпросмотром.
- Правила подсчёта: уникальные компьютеры; уязвимые установки (компьютер × программа); обнаружения KSC (компьютер × уязвимость × программа); распределение по опасности — по наивысшему уровню на компьютер, сумма равна числу компьютеров. Выбор нескольких уязвимостей не удваивает компьютеры.
- «Связывался с KSC за N суток» и «в сети сейчас» — разные условия: по умолчанию учитываются устройства, связывавшиеся за период; «в сети сейчас» — отдельный фильтр, а в результатах всегда есть столбец «В сети сейчас». Если KSC не передаёт флаг присутствия, это отмечено, и фильтр не применяется молча.
- Достоверность: отчёт различает уязвимости, подтверждённые KSC, и результат проверки версий по условию пользователя; записи без привязки уязвимости к установленной версии, скрытые неактивные компьютеры и записи кластеров перечислены в замечаниях.
- Excel: листы «Сводка», основная таблица, «Компьютеры», «Программы», «Уязвимости», «Параметры»; фильтры, сортировка, закреплённый заголовок, подобранная ширина. HTML: самодостаточный документ для руководства (показатели, распределение по опасности, условия, замечания, таблицы), без внешних ресурсов и скриптов, печать и PDF средствами браузера; HTML есть и у проверки версий.
- Предпросмотр строится из того же документа, что и файлы, и кэшируется: числа в просмотре и готовом отчёте совпадают, повторное открытие не читает KSC заново. Файлы формируются фоновым воркером; готовый отчёт открывается в «Отчётах» (просмотр, повтор, скачивание XLSX, CSV, HTML).

- События безопасности: устройства, которых уже нет в KSC, показываются как «Удалённое устройство (ID …, имя неизвестно)», IP-адрес — «нет данных» (в публичном представлении KSC имя на момент события недоступно); в отчёте это отмечено и посчитано. Отчёт по событиям читает журнал одним запросом вместо постраничного чтения с повторным подсчётом: 15 тыс. событий за 30 суток на базе из 300 тыс. событий — 2,4 с вместо 16 с, повторный просмотр из кэша без запросов к SQL Server.
- HTML-отчёт при сокращении выборки (больше 3 000 строк в таблице) явно предупреждает об этом вверху документа и в панели предпросмотра; показатели сводки (компьютеры, установки, обнаружения) всегда посчитаны по полному результату, полный список — в Excel и CSV.
- Список уязвимостей на очень большой базе (650 тыс. обнаружений) загружается за 15 секунд вместо двух минут: группировка только по идентификатору уязвимости, имена и ссылки — отдельным небольшим запросом.

## [0.2.0] — 2026-10-24

- Каталог программ: записи реестра KSC автоматически объединяются в продукты и ветки (Google Chrome, Firefox, Java, PHP, Python, OpenSSL и другие), с производителями, версиями и числом компьютеров; ошибочную группировку можно исправить вручную.
- Проверка версий: выберите программу и версию, ниже которой она устарела, — получите компьютеры и XLSX. Несколько программ и несколько серверов KSC в одной проверке; исключение версий и веток; целевая версия; проверку можно сохранить и запускать повторно.
- Сравнение версий учитывает тип продукта: пакеты Linux, программы Windows, нестандартная нумерация Java и Python.
- Раздел «Уязвимости» начинается с самых проблемных компьютеров; есть вид по уязвимым программам и карточка компьютера с CVE, KB и наличием исправления.
- Давно не подключавшиеся компьютеры скрыты в рабочих разделах (по умолчанию — неактивные дольше 30 суток), их можно показать одной кнопкой. Порог 7 суток из 0.1.0 заменён на 30.
- Выбранный источник KSC запоминается для каждого пользователя.
- Раздел «Состояние защиты»: компьютеры без антивируса, с неработающей защитой, устаревшими базами, невылеченными объектами, истёкшей лицензией, без свежей полной проверки и ожидающие перезагрузки; пороги баз и проверки выбираются на странице; версии Kaspersky Endpoint Security и Агента администрирования по числу компьютеров с переходом к списку; причины статуса KSC.
- Раздел «События безопасности»: обнаружения, невылеченные объекты, обработанные угрозы и сетевые атаки за сутки, 7 или 30 суток; динамика, компьютеры и угрозы с наибольшим числом событий, журнал обнаружений с поиском по компьютеру, угрозе, объекту и пользователю.
- Карточка компьютера: проблемы защиты в заголовке, вкладки «Установленное ПО», «Уязвимости» и «События безопасности».
- Главная: блок «Защита и угрозы» и частые задачи аудита.
- LDAP: несколько подключений (домены) с выбором основного, вход как `EXAMPLE\user` или `user@example.local`; загрузка корневых и промежуточных сертификатов ЦС (PEM, DER, текст) с проверкой срока и отказом принять закрытый ключ; доступ по группам каталога: группа → роль и источники KSC; поиск групп в каталоге; пошаговая диагностика (DNS, TCP, TLS, цепочка сертификатов, вход сервисной записи, поиск пользователя, группы) и проверка, какой доступ получит пользователь. Настройки LDAP из 0.1.0 переносятся автоматически.
- Второй фактор (TOTP, приложения-аутентификаторы) с резервными кодами; политика: отключён, по желанию, обязателен администраторам, всем или группам каталога; администратор может сбросить второй фактор пользователя.
- Работа за reverse proxy по HTTP и HTTPS: флаг Secure у cookie включается сам, когда адрес приложения — https:// (`COOKIE_SECURE=auto`).
- Обновления: проверки перед обновлением (место на диске, доступ к GitHub и реестрам, внутренняя база, возможность отката) — кнопкой и перед каждым обновлением; приложение останавливается на время резервной копии и миграций; при ошибке миграции база возвращается к копии, неудачная сохраняется под другим именем, код и образы — к прежней версии; отчёт о последнем обновлении с выполненными действиями; восстановление копии из браузера с подтверждением; хранятся образы текущей и одной предыдущей версии.
- Зеркала npm и pip для установки и обновления без доступа к официальным реестрам (`NPM_REGISTRY`, `PIP_INDEX_URL`, `install.sh --npm-registry`); проверка контрольных сумм пакетов сохраняется; локальные правки зеркала на сервере переносятся в `.env` при обновлении.
- Состояние системы: компоненты, процессор, память, диски, размер базы, отчётов, резервных копий и образов, ошибки фоновых задач, история обновлений, безопасность. Журнал событий: произвольный период и фильтр по компоненту.

- Проект открыт под лицензией MIT.
- Новый облик интерфейса: графитовое меню, единый акцент, шрифты Onest и JetBrains Mono, собственные пиктограммы.
- «Спектр версий»: доли версий и веток наглядно, выбор щелчком.
- Тема «как в системе» по умолчанию, светлая и тёмная выбираются в меню пользователя.
- Удобнее с клавиатуры и на телефоне: Escape и стрелки в меню и окнах, выдвижное меню, окна в виде нижнего листа.

### Исправлено

- Восстановление резервной копии поверх более новой схемы базы давало смешанную базу; теперь копия восстанавливается в чистую базу, прежняя сохраняется под другим именем.
- «Обновить» в разделе «Уязвимости» больше не перечитывает данные KSC при каждой следующей странице.

### Обновление с 0.1.0

- Если registry.npmjs.org недоступен с сервера, перед обновлением добавьте в `.env` строку `NPM_REGISTRY=<адрес зеркала>` (например, `https://npm-mirror.gitverse.ru`): обновление собирает интерфейс локально.
- Правки файлов проекта, сделанные на сервере вручную (например, адрес зеркала в `frontend/Dockerfile`), обновление 0.1.0 откладывает в `git stash`; после обновления адрес зеркала задаётся только в `.env`.
- Порог активности 7 суток, сохранённый в 0.1.0, заменяется на 30; другое значение сохраняется.
- Подключение LDAP из 0.1.0 и его группы ролей переносятся в новые подключения и правила доступа при первом запуске.
- Откат с 0.2.0 на 0.1.0 требует восстановления копии базы, снятой перед обновлением: Администрирование → Обновления → «Резервные копии» → «Восстановить», затем «Откатить версию».

## [0.1.0] — 2026-10-23

Первый выпуск.

- Административная панель: левое меню, верхняя панель с переключателем источника KSC, светлая и тёмная темы.
- Локальные учётные записи, LDAP/LDAPS, роли (администратор, аналитик, просмотр), доступ к отдельным источникам.
- Источники KSC: несколько подключений к SQL Server только для чтения, проверка с диагностикой (версия SQL Server, версия KSC, объекты, права).
- Реестр установленного ПО с поиском и счётчиками установок и уникальных компьютеров; группировка по продуктам и веткам версий; встроенное правило PHP.
- Выбор версий и диапазонов, список компьютеров с фильтром активности, сохранение сценариев аудита.
- Компьютеры и активность, карточка компьютера с ПО и продуктами Kaspersky; уязвимости, подтверждённые KSC.
- Отчёты: конструктор, фоновое формирование, отмена, повтор, шаблоны, экспорт XLSX и CSV.
- Журнал действий, журнал событий, состояние системы, обновления и откат через GitHub, резервные копии.
