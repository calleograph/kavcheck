# Архитектура

## Компоненты

```
Браузер ──HTTPS──► внешний reverse proxy (TLS) ──► web (nginx + React SPA)
                                                      │ /api/ → backend (FastAPI)
                                                      │              ├── postgres (внутренняя база)
                                                      │              └── SQL Server баз KSC (только чтение, pymssql)
                                                   worker (тот же образ backend, python -m app.worker) ──► report_jobs → DATA_ROOT/reports; каталог программ
                                                   помощник обновлений на хосте (scripts/updater.sh) ◄── DATA_ROOT/updater
```

| Сервис | Технология | Ответственность |
|---|---|---|
| `web` | nginx unprivileged + собранный React/TypeScript | статика, прокси `/api/` к backend, заголовки безопасности и CSP |
| `backend` | Python 3.12, FastAPI, SQLAlchemy async, Alembic | вход (локальный, LDAP, второй фактор), сессии, роли, источники KSC, каталог и реестр ПО, компьютеры, уязвимости, состояние защиты, события безопасности, проверки версий и отчёты (постановка и выдача), настройки, журналы, состояние системы |
| `worker` | тот же образ | фоновое формирование отчётов (опрос `report_jobs`, XLSX/CSV, отмена, очистка по сроку) и построение каталога программ по источникам (`CatalogScheduler`); пульс в `service_heartbeats` |
| `pentest` | тот же образ (с Nmap), `python -m app.pentest.worker` | сканер Pentest: очередь заданий сетевого сканирования, запуск Nmap без shell, разбор XML потоком, изоляция ошибок и восстановление; `cap_drop: ALL`, без доступа к данным отчётов; подробно — [PENTEST.md](PENTEST.md) |
| `postgres` | PostgreSQL 16 | внутренняя база: пользователи, сессии, второй фактор, подключения LDAP, сертификаты CA, правила доступа, настройки, источники, каталог и ручные правки, сохранённые проверки, отчёты, журналы, кэш главной |

Контейнеры работают не от root, с `no-new-privileges`, перезапускаются после перезагрузки сервера (`restart: unless-stopped`), имеют healthcheck. Наружу публикуется только порт web (по умолчанию loopback).

## Данные

- Внутренняя база — только через Alembic (`backend/migrations`). Модели — `backend/app/models.py`.
- `DATA_ROOT`: `postgres/`, `reports/<job_id>/{rows.jsonl,report.xlsx,report.csv}`, `backups/`, `updater/` (канал с помощником), `state/`.
- Базы KSC не изменяются никогда.

## Безопасность

- Сессии серверные (таблица `sessions`, в cookie только случайный идентификатор, HttpOnly, SameSite=Lax, Secure — при HTTPS, `COOKIE_SECURE=auto`); CSRF-токен в заголовке `X-CSRF-Token`, проверка Origin по `APP_PUBLIC_URL`/`ALLOWED_ORIGINS`.
- Второй фактор TOTP (RFC 6238): секрет зашифрован, резервные коды хранятся как HMAC; незавершённый вход — одноразовый вызов в таблице `auth_challenges` с ограничением попыток; сессия с обязательным, но не подключённым вторым фактором допускается только к его настройке.
- LDAP: только LDAPS или STARTTLS с обязательной проверкой сертификата (загруженные CA или системное хранилище), значения в фильтрах экранируются, роль и источники — по правилам доступа на каждом входе.
- Защита от перебора паролей: блокировка логина после N неудач.
- Роли проверяются зависимостями FastAPI (`require_user`, `require_analyst`, `require_admin`); доступ к источнику — `current_source` на каждом запросе.
- Пароли источников и LDAP, секреты второго фактора зашифрованы AES-256-GCM (`APP_MASTER_KEY` из окружения, связанные данные — идентификатор записи), не возвращаются API, маскируются в журналах.
- SQL к KSC: только шаблоны с параметрами, `guard.check` до подключения, `READ UNCOMMITTED` и `LOCK_TIMEOUT` на соединении, тайм-ауты, предел строк, семафор одновременных запросов на источник, учётная запись только для чтения (диагностика предупреждает о правах на запись).
- Обновления из браузера — через помощника с белым списком действий; значения запроса проверяются по шаблонам, устаревшие и чужие запросы отбрасываются.

## Слои backend

```
api/*.py          маршруты (тонкие), схемы pydantic (api/schemas.py)
auth/             сессии, зависимости и роли, LDAP, сценарий входа
services/         настройки (группы), аудит и журнал, реестр клиентов источников, кэш (TtlCache), каталог (хранение, планировщик), LDAP (подключения, CA, правила), обновления, состояние системы
security/         шифрование секретов, пароли, TOTP, разбор сертификатов
ksc/              адаптер KSC: driver (pymssql), guard, queries (шаблоны), schema (диагностика/совместимость), versions, catalog и catalog_build (продукты и ветки),
                  software, hosts, dashboard, vulns, protection, events
reports/          builder и audit (виды отчётов, проверка версий), export (JSONL/CSV/XLSX), runner (воркер), quick/quick_ext (документ отчёта), quick_export и layout (HTML/XLSX, единый порядок таблиц)
zones/            зоны ответственности: match (принадлежность по сетям/группам, приоритеты), csv_io, service, dataset (запись «компьютер × проблемы»), report (отчёт зоны),
                  triage (решения по уязвимостям), schedule и mailer (расписания, устойчивая очередь рассылки); snapshot (потоковый расчёт подготовленных данных зон), zread (чтение агрегатами SQL),
                  zjobs (очередь заданий, ночное расписание, восстановление), reporter (данные для отчётов); services/mail — SMTP; services/resources — ограничитель ресурсов worker (память, конкуренция)
```

## Совместимость с версиями KSC

Шаблоны опираются на публичные представления `v_akpub_*` и внутренние таблицы реестра ПО и уязвимостей, проверенные на KSC 15.1. При добавлении источника проверяется наличие объектов для каждой функции (`ksc/queries.py: FEATURE_OBJECTS`); отсутствующие функции помечаются как недоступные для источника, остальные работают. Проверка версий выполняется по нескольким источникам сразу; каждая строка результата хранит источник, отчёт — время получения данных.

## EOL, устройства и пользователи

* `app/eol/` — жизненный цикл ПО и ОС: `classify` (правила), `osmatch` (ОС → ветка), `sync` (загрузка endoflife.date), `compute` (сопоставление каталога и ОС, устройства), `service` (фоновый пересчёт), `read` (чтение для страниц). Подробно: [EOL.md](EOL.md).
* `app/ksc/hardware.py` — сводка оборудования устройства из `hst_hwinv_dev` и оценка ресурсов Linux-серверов (ядра, ОЗУ). Подробно: [HARDWARE.md](HARDWARE.md).
* `app/vdb/classify.py`, `classmap.py` — категории продуктов для плана устранения; `app/reports/xlsx.py` — потоковая запись XLSX; `app/services/cache.py` — кэш с «устаревшее допустимо» (SWR); `app/db.py` — подключение (отдельные тайм-ауты worker) и `xact_lock`.
* `app/overview/` (показатели главной, срезы), `app/licensing/` (лицензии, общие пулы) — [DASHBOARD.md](DASHBOARD.md); `app/pentest/` (цели, Nmap, сканер, анализ, OVAL) — [PENTEST.md](PENTEST.md).
* `app/services/jobs.py` — аренды и история фоновых заданий (восстановление после сбоя, координация worker, ограждение результата); подробно — [JOBS.md](JOBS.md).
* `app/devices/` — опрос пользователей KSC (`users`, `service`) и чтение таблицы устройств (`read`). Подробно: [DEVICES.md](DEVICES.md).
* `app/netsearch.py` — единый поиск (имя, IP, CIDR, диапазоны, логин) для всех списков устройств.
* `auth/deps.py: source_scope` — «Все источники» (`X-Source-Id: all`).

## Память и фоновые задачи

Тяжёлые операции выполняет только worker и только порциями: анализ уязвимостей (`vdb/sync.analyze`: записи источников читаются строками по 300 уязвимостей, результат фиксируется после каждой порции), сборка каталога, расчёт зон (`zones/snapshot`) и отчёты. Они делят `services/resources.RES`: по умолчанию одна тяжёлая задача за раз, мягкий предел памяти откладывает новые задачи, жёсткий останавливает текущую на границе порции (она повторяется с сохранённого места или с начала без видимых изменений). Страницы зон читают только подготовленные данные PostgreSQL ([ZONE_CACHE.md](ZONE_CACHE.md)); backend не читает KSC для дашбордов и не загружает источники в память. Измерения — [PERFORMANCE.md](PERFORMANCE.md).

## Нагрузка на SQL Server

- Каталог программ строится в worker постранично (keyset по компьютерам, продуктам и установкам), не чаще необходимого: при первом подключении, по запросу, при изменении реестра (подпись проверяется каждые 15 минут) и не реже раза в 12 часов. Пользовательские разделы читают готовый каталог из внутренней базы.
- Сводки уязвимостей и состояния защиты — один агрегирующий запрос на источник, кэш в памяти процесса на `CACHE_TTL_SECONDS`; фильтры, пороги, сортировка и страницы — по кэшированному набору.
- События безопасности: каждый запрос ограничен периодом (`tmRiseTime`, до 90 суток) и типами обнаружений; сводка кэшируется, журнал — постранично.
- Проверка производительности — синтетическая база KAVBIG (20 тыс. компьютеров, 600 тыс. установок, 660 тыс. уязвимостей, 300 тыс. событий): каталог строится за 14 с, сводка защиты — около 5 с без кэша, сводка событий за 30 суток — около 1 с.

## Будущие модули

Аудит лицензий, сравнение периодов, сводные отчёты по нескольким KSC для разделов кроме проверки версий. Они используют те же компоненты: источники, роли, фильтр активности, построитель отчётов и экспорт, журналирование.
