# Проверка 0.9.3 на рабочих источниках KSC

Короткая инструкция для установки с реальными большими базами. Все обращения к KSC — только чтение. Выполняйте на тестовом экземпляре или в нерабочее время; рабочую установку обновляйте только после успешной проверки.

Команды даны для каталога установки (`docker compose` из каталога с `.env`). Имена источников — как в «Администрирование → Источники KSC».

## 0. До обновления: запомните исходное состояние

```bash
docker stats --no-stream            # память worker, backend, postgres
docker compose exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select pg_size_pretty(pg_database_size(current_database()))"
```

## 1. Обновление и миграции

После обновления проверьте: `docker compose ps` (все `healthy`, у worker тоже), `docker compose exec backend alembic current` → `0013_vdb_plan`. PostgreSQL перезапустится с новыми настройками (`PG_*`) и лимитом `POSTGRES_MEM_LIMIT` (2 ГБ по умолчанию; для 16 ГБ ОЗУ можно поднять, см. `.env.example`).

## 2. EOL (главная проверка)

```bash
docker compose exec worker python -m app.tools.perf eol --source "kav01"
docker compose exec worker python -m app.tools.perf eol --source "kav02"
```

Ожидается: нет `UniqueViolation`, выводятся время, пик памяти (RSS), число находок и связей «устройство — находка». Запишите числа. Затем в интерфейсе **EOL**:

- состояние каждого источника — «Готово» (не «Ошибка», не «Не рассчитано»); число EOL-программ и устройств больше нуля, если на устройствах есть ПО без поддержки;
- выберите 3–5 находок и сверьте: продукт и ветка соответствуют установленной версии, даты — с endoflife.date; у устройств в списке переход в карточку работает;
- спорные продукты — вкладка «Соответствия»: назначьте продукт или исключите, после «Пересчитать» состояние «Выполняется» сменится на «Готово»;
- журнал: `docker compose logs worker | grep -i "eol"` — без ошибок.

## 3. Уязвимости: правильность цифр

«База уязвимостей → Затрагивают нашу инфраструктуру» (дождитесь окончания анализа: плашка «идёт подготовка плана» исчезнет).

- Сравните «Уникальных уязвимостей» со строкой «Достоверность»: подтверждено + потенциально + требует уточнения + недостаточно данных = всего.
- Вид «План устранения»: для 3–5 крупных продуктов откройте уязвимости и нажмите «Проверить» — число компьютеров в проверке должно быть близко к «≈» в плане (в плане компьютер с несколькими версиями считается по каждой).
- Проверьте категории: ОС, системные компоненты, прикладное ПО; продукты с неверной категорией переназначьте в строке плана. Список «Не классифицировано» — кандидаты на ручное назначение.
- Карточка компьютера → «Уязвимости»: продукты со счётчиками; раскройте продукт с большим числом CVE — «Показано 25 из N», счётчик на вкладке совпадает с суммой.

## 4. Память и PostgreSQL

Во время полного цикла (после обновления worker сам запускает анализ, каталог, расчёт зон и EOL) наблюдайте:

```bash
watch -n 10 'docker stats --no-stream --format "{{.Name}} {{.MemUsage}}"'
```

и «Администрирование → Состояние системы → Фоновые расчёты» (пик памяти worker, длительность по источникам, долгие транзакции PostgreSQL). Ориентиры: worker ниже мягкого предела (50 % `WORKER_MEM_LIMIT`), без перезапусков (`docker compose ps` — время работы не обнуляется); postgres ниже `POSTGRES_MEM_LIMIT`. Долгих транзакций (> минуты) в «простое» нет.

Медленные запросы PostgreSQL (порог 2 с):

```bash
docker compose logs postgres | grep "duration:" | tail -20
```

Если они есть — приложите запрос и длительность к обращению.

## 5. Отчёты

1. «Отчёты → Проверка версий»: выберите программу, **зону не выбирайте**, источник `kav02` — запуск без ошибки.
2. Тот же отчёт по нескольким источникам; повторный запуск; запуск из сохранённой проверки.
3. Быстрый отчёт на крупной выборке (порядка 100 тыс. строк): в «Состоянии системы → Фоновые расчёты» — длительность отчётов; во время формирования память worker (`docker stats`) не должна расти пропорционально числу строк (ориентир: пик ≈ 250 МБ на отчёт со 100 тыс. строк).
4. Двойной щелчок на «Сформировать» создаёт одно задание.

## 6. Отказоустойчивость

- `docker compose restart worker` во время расчёта: после старта состояние «Выполняется» сбрасывается, расчёт запускается заново, прежний результат остаётся.
- Остановите worker на минуту (`docker compose stop worker`), затем запустите: очередь отчётов продолжается, ошибок первичного ключа нет.

## Что прислать, если что-то не так

Версия (`Состояние системы`), вывод `perf` из п. 2, скриншот блока «Фоновые расчёты», `docker compose logs --since 1h worker`, медленные запросы из п. 4. Не присылайте имена компьютеров и учётные записи — маскируйте.
