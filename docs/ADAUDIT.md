# Аудит домена (Active Directory)

Раздел «Защита и уязвимости → Аудит домена» (`/adaudit`) заменяет ручной сбор сведений PowerShell-скриптами. Раз в месяц (и раз в квартал) администратор получает полную картину по учётным записям домена. Он видит нарушения и спорные случаи, записывает решения: устранено, согласованное исключение, ответственный, срок. По итогам формируется документированный отчёт.

**Раздел только читает домен.** Он не отключает и не блокирует учётные записи, не сбрасывает пароли и вообще ничего не меняет в AD. Доступ: специалист по ИБ и администратор. Настройки: «Администрирование → Правила анализа → Аудит домена» (только администратор).

## Откуда данные

| Сведения | Источник | Точность |
|---|---|---|
| Учётные записи, состояние, флаги (`userAccountControl`, `msDS-User-Account-Control-Computed`), даты создания, смены пароля (`pwdLastSet`), срок действия (`accountExpires`), описание, ответственный (`manager`, `info`), группы | LDAPS. Используется то же подключение, что в «Администрирование → LDAPS», и его сервисная учётная запись; второго подключения к домену нет | на момент проверки |
| Привилегированные группы (Domain Admins, Enterprise Admins, Schema Admins, Administrators, Account/Server/Backup/Print Operators и группы из настроек), Protected Users | LDAP с учётом вложенности (`LDAP_MATCHING_RULE_IN_CHAIN`) и первичной группы | точно |
| Последний вход | `lastLogon` с **каждого** контроллера домена (атрибут не реплицируется), берётся максимум | точно, если ответили все контроллеры |
| | иначе `lastLogonTimestamp` | реплицируется с задержкой до ~14 суток; источник указан в каждой строке |
| Смена (4723) и сброс (4724) пароля | журналы Security контроллеров: выгрузка скриптом и загрузка файла (см. ниже). LDAP истории операций не хранит | в пределах охвата загруженных журналов |

Сбор выполняет worker фоновым заданием под арендой `adaudit`. Каталог читается постранично: учётных записей до 300 000, на каждый контроллер отдельный проход. Ход и ошибки видны в «Техническом состоянии» и в журнале событий (категория «Аудит домена»). Пароли и секретные атрибуты не запрашиваются и не хранятся.

## Активные учётные записи

По умолчанию сводка, списки, замечания, состав групп, события паролей и отчёты сохранённого аудита показывают активные учётные записи на дату выбранной проверки. Запись включена, блокировка не зафиксирована и срок самой учётной записи не истёк. Давний вход и истёкший пароль остаются основаниями для проверки.

Переключатель «Включить неактивные учётные записи» расширяет отбор на весь сохранённый снимок. Выбор действует при переходе между вкладками и передаётся в новый отчёт вместе с фильтрами и номером проверки. Отключение, удаление и прежнее членство выбывших записей видны в расширенном отборе. Сбор сохраняет все записи и решения, доступ к ним остаётся у специалиста по ИБ и администратора.

Блокировка берётся из вычисленного состояния AD. Если оно недоступно, сохранённый снимок использует `lockoutTime` без учёта автоматического окончания блокировки. Состояние можно уточнить в живом каталоге. [Атрибуты состояния AD](https://learn.microsoft.com/en-us/windows/win32/ad/user-object-user-interface-mapping)

## Категории учётных записей

Категории: пользователь, административная, сервисная, временная, подрядчик и **«Не определено»**. Правила задаёт администратор.

- **Сильные признаки:** группа (CN или DN, с учётом вложенности), подразделение (OU), атрибут (`employeeType=contractor`). Чтобы назначить категорию, достаточно одного сильного признака.
- **Слабые признаки:** имя (маска `svc*`), описание (`*сервисн*`), наличие `servicePrincipalName`. Нужны **два согласных** слабых признака. Одно имя или одно описание — не основание: такая запись попадает в «Не определено».
- Членство в привилегированной группе — всегда «административная». Противоречивые сильные признаки дают «Не определено».
- Ручное решение в карточке учётной записи важнее правил и применяется со следующей проверки.

Основания категории показываются в карточке и в отчётах.

## Проверки

Сроки смены пароля по категориям настраиваются. По умолчанию: пользователь — 90 дней, административная — 30, сервисная — 180, временная и подрядчик — 90.

| Замечание | Когда |
|---|---|
| Пароль без срока действия (Password Never Expires) | у включённых: административная — критическое; пользователь, временная, подрядчик — высокое. **Сервисная** — «требует дополнительной проверки» (допустимо как согласованное исключение с ручной сменой не реже раза в 180 дней), нарушение — если пароль старше 180 дней |
| Пароль не менялся дольше срока категории | точная дата и число дней; группы давности «до 30 / 30–90 / 90–180 / более 180 / дата неизвестна» |
| Пароль не сменён после выдачи | `pwdLastSet = 0` дольше срока на первый вход (по умолчанию 14 дней) |
| Учётная запись не используется / ни разу не использовалась | нет входа дольше порога (по умолчанию 90 дней) |
| Временная или подрядная без срока действия | `accountExpires` не задан |
| Срок действия истёк, учётная запись включена | требует проверки |
| Пароль не обязателен (PASSWD_NOTREQD), обратимое шифрование, отключена предварительная проверка Kerberos | флаги `userAccountControl` |
| Административная вне Protected Users | с учётом вложенности (отключается в настройках) |
| Сервисная без описания назначения / без ответственного / в привилегированной группе | Description, `manager`/`info`, членство |
| Ограничение интерактивного входа не подтверждено | у административных и сервисных без `userWorkstations`: запрет входа задаётся групповыми политиками, по атрибутам AD его не проверить — **требует дополнительной проверки** |
| Последняя операция с паролем — сброс (Reset Password) | см. ниже; строки выделяются красным |
| Категория не определена | требует ручной классификации |

Отключённые учётные записи проверяются только на флаги, опасные и при отключении.

## Смена и сброс пароля (4723 / 4724)

Штатный порядок: пользователь меняет пароль сам (Change Password, событие **4723**). Сброс другой учётной записью (Reset Password, **4724**) требует проверки.

Способ последней операции определяется так. Берётся успешное событие (по признаку Audit Success) в пределах 10 минут от `pwdLastSet` той же учётной записи; цель сопоставляется по SID, а если SID нет — по логину. Неуспешная попытка операцией не считается. Состояния:

- **смена пользователем** или **сброс**: событие совпало с `pwdLastSet`. «Сброс без последующей смены» — замечание высокой важности. Для новой учётной записи в пределах срока на первый вход замечания нет: её первый пароль выдаётся сбросом.
- **событие не найдено**: пароль изменён в период, охваченный журналами **всех** контроллеров, но события нет (аудит на контроллере мог быть выключен). Требует дополнительной проверки, нарушением не считается.
- **раньше сохранённых журналов** / **журналов нет**: вывода нет. Если журнал хотя бы одного известного контроллера отсутствует, отсутствие события ни о чём не говорит.

### Как загрузить журналы

1. Учётная запись, от имени которой запускается скрипт, должна входить во встроенную группу домена **Event Log Readers** (`Builtin\Event Log Readers`, действует на всех контроллерах). Права администратора домена **не нужны**. Сервисную учётную запись LDAPS для этого расширять не требуется.
2. На контроллерах:
   - включён аудит «Аудит управления учётными записями пользователей» (Audit User Account Management: Success, Failure);
   - разрешено правило брандмауэра «Удалённое управление журналом событий» (RPC).
   Размер журнала Security определяет глубину истории.
3. Запустите на любом компьютере домена: `scripts/windows/Export-KavPasswordEvents.ps1 -Days 120 -OutFile pwd-events.json`. Скрипт только читает. Он выгружает события 4723/4724 и охват журнала каждого контроллера (первое и последнее событие).
4. В разделе: «Смена и сброс пароля → Загрузить журналы (JSON)». Повторы не дублируются. События учитываются при следующей проверке.

## Ежемесячная процедура

1. Проверка выполняется по расписанию (день месяца, время, часовой пояс). В квартальные месяцы (по умолчанию 1, 4, 7, 10) она квартальная. Внеплановую или квартальную можно запустить кнопкой.
2. Каждая проверка сохраняется отдельным снимком: учётные записи, категории, замечания. Для каждого замечания видно, когда оно впервые обнаружено и сколько проверок подряд повторяется. Видно, что появилось нового и что устранено с прошлой проверки. История — вкладка «Проверки»; любую прежнюю проверку можно открыть.
3. Решения по замечаниям живут между проверками:
   - **в работе** — с ответственным и сроком;
   - **отмечено устранённым** — если замечание найдено снова, оно возвращается в «не решённые»;
   - **согласованное исключение** — основание обязательно; можно указать срок, после которого исключение истекает.
   Все решения и их история пишутся в журнал действий.
4. Квартальная проверка: в отчёте «Неиспользуемые учётные записи и давние пароли» — включённые без входа дольше порога и с паролем старше 180 дней.

## Отчёты

Отчёты есть на каждой вкладке и в «Быстром доступе» («Аудит домена: сводка для руководства»). Вид отчёта `quick_adaudit`, форматы XLSX, CSV, PDF, HTML. Источник — сохранённая проверка, по умолчанию последняя.

| Вид | Содержание |
|---|---|
| `accounts`, `active` | учётные записи в выбранном режиме или только активные |
| `pne` | пароль без срока действия |
| `pwd_age` | давность смены паролей по группам |
| `resets` | сброс без последующей смены и события 4724 |
| `events` | события смены и сброса пароля по фильтрам списка |
| `unused` | неиспользуемые и давние пароли (квартальная проверка) |
| `privileged` | административные и сервисные: группы, Protected Users, основание категории |
| `findings` | все замечания с решениями |
| `audit` | результаты проверки: замечания, оставшиеся с прошлых проверок, устранённые |
| `groups` | состав привилегированных групп, добавленные и исключённые с прошлой проверки |
| `changes` | изменения учётных записей с прошлой проверки |
| `summary` | для руководства: состояние домена, замечания по видам, категориям и подразделениям (OU), динамика по проверкам, наиболее существенные нарушения |

В строках — учётная запись, подразделение (OU), состояние учётной записи, даты, основание замечания, категория, статус проверки, решение, ответственный, срок и комментарий. В конструкторе отчёта строки можно сгруппировать по подразделению. Отчёт содержит персональные данные.

## Подразделения (OU)

Подразделение — путь контейнеров от корня домена без самой учётной записи и компонентов DC: для `CN=Иванов,OU=Бухгалтерия,OU=Офис,DC=example,DC=local` это `Офис/Бухгалтерия`; учётная запись прямо в корне домена — «корень домена». Подразделение показывается под логином в замечаниях и списках учётных записей и в карточке. Нажатие на него оставляет в списке только это подразделение.

- Отбор «Подразделение (OU)» в «Все фильтры» на вкладках «Замечания» и «Учётные записи», а также на вкладках «Активность» и «Админ. и сервисные»: часть пути или маска со `*` (`*Подрядчики*`), подсказки — подразделения проверки. Отбор передаётся в отчёт. Поиск по тексту тоже находит учётные записи по подразделению.
- «Обзор → Подразделения (OU)»: где больше всего замечаний, требующих внимания (сначала критические и высокие). Число переходит к замечаниям подразделения, число учётных записей — к их списку.
- Замечания можно отобрать по состоянию учётной записи (активная или отключённая). Флажок в заголовке таблицы выбирает все загруженные замечания для общего решения.

Подразделение сохраняется в проверке (`ad_audit_accounts.ou`, миграция 0039 заполняет его и для прежних проверок по DN). `GET /adaudit/ous` — подразделения проверки с числом учётных записей и замечаний.

## Политика проверки

Вкладка «Политика» показывает текущие сроки смены пароля по категориям, пороги активности (неиспользуемая, недавно созданная, срок на первый вход), требование Protected Users, дополнительные привилегированные группы и **основание политики** — например, приказ или требования конкретного предприятия («пароль администраторов — не реже раза в 90 дней»). Администратор KAV Checker меняет политику прямо здесь (`PUT /adaudit/policy`, журнал действий `adaudit.policy`); подключение, расписание и правила классификации — в «Администрирование → Аудит домена».

Политика применяется со следующей проверки. Каждая проверка хранит политику, по которой она выполнена (`ad_audit_runs.policy`). Таблица «Политика по проверкам» (`GET /adaudit/policies`) показывает, когда менялись сроки; политика проверки выводится в шапке каждого отчёта. Если политика изменена после последней проверки, вкладка об этом предупреждает: замечания последней проверки посчитаны по прежним срокам.

## Группы, изменения, каталог

- **Группы** — участники привилегированных групп (Domain Admins, Enterprise Admins, Schema Admins, Administrators, Account/Server/Backup/Print Operators и группы из политики) с учётом вложенности и первичной группы; кто добавлен и кто исключён по сравнению с предыдущей проверкой. Отчёт — вид `groups`.
- **Изменения** — что изменилось с предыдущей проверки: новые и удалённые учётные записи, отключённые и снова включённые, смена категории, перемещение в другое подразделение (OU), получение и потеря привилегий. Учётные записи сопоставляются по objectGUID (переименование — не удаление); считается в SQL, в ответе — не больше 2000 записей каждого вида. Отчёт — вид `changes`.
- **Каталог AD** — живой поиск в домене: пользователи и группы, свойства, членство (непосредственное, первичное, вложенное — отдельно), участники группы. У каталога свой отбор и отчёты. Переключатель активных учётных записей применяется к сохранённым проверкам аудита. Каталог использует тот же компонент и API, что во вкладке «Active Directory» раздела «Иерархия» (`app/ad/`, [HIERARCHY.md](HIERARCHY.md#active-directory-вкладка-в-разделе)). Из карточки учётной записи аудита доступна кнопка «Открыть в каталоге AD».

## Что не проверяется по атрибутам AD

- Запрет интерактивного входа через групповые политики (Deny log on locally / through RDP).
- Фактическая ротация пароля сервисной учётной записи вне AD (gMSA, хранилища паролей).
- Членство в группах других доменов леса.

Такие проверки получают статус «Требует дополнительной проверки». Разделу нужен Active Directory: каталоги без `userAccountControl` и `pwdLastSet` (OpenLDAP) не поддерживаются.

## Для разработчиков

`backend/app/adaudit/`:
- `collect.py` — чтение каталога (синхронно, в потоке);
- `checks.py` — категории, способ операции с паролем, замечания (чистые функции);
- `events.py` — разбор выгрузки событий;
- `service.py` — расписание, задание под арендой, снимок одной транзакцией с `fence`, перенос замечаний, хранение;
- `diff.py` — состав привилегированных групп и изменения между проверками (общие для API и отчётов).

API — `api/adaudit.py`, отчёт — `reports/quick_adaudit.py`, страница — `pages/AdAuditPage.tsx`, настройки — группа `adaudit` (`AdAuditSettings`), вкладка `admin/AdAuditAdmin.tsx`. Таблицы `ad_audit_*`, `ad_class_overrides`, `ad_event_imports`, `ad_pwd_events` (миграция 0034). Тесты на синтетическом каталоге — `tests/test_adaudit.py`.
