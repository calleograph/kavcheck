# EOL: жизненный цикл программ и операционных систем

Раздел «EOL» показывает, какие программы и ОС вашей инфраструктуры вышли из поддержки производителя или выйдут в ближайшее время. Сроки берутся из открытой базы [endoflife.date](https://endoflife.date) (API v1).

## Откуда данные и как они обновляются

* Источник `endoflife.date` — один из источников подсистемы баз уязвимостей («Администрирование → База уязвимостей»). Он включён по умолчанию, расписание — раз в сутки, ручной запуск — кнопкой источника.
* Загружается один документ `GET /api/v1/products/full` (все продукты и ветки). Запрос условный (ETag): если на сайте ничего не менялось, ответ `304`, ничего не читается. Если изменилось — сравнивается хэш каждого продукта, **записываются только изменившиеся**, исчезнувшие удаляются (`eol_products`, `eol_releases` в PostgreSQL).
* Сайт недоступен или вернул неверный документ — загрузка заканчивается ошибкой, **прежняя копия остаётся** и используется; раздел показывает дату последнего успешного обновления и причину сбоя. Проверка на полностью отключённом от интернета сервере: источник отметит ошибку, остальное продолжит работать на загруженной ранее копии.
* Файл с данными можно подложить вручную так же, как для других источников (канал «файл»), если сервер не имеет выхода в интернет.

## Что значит «EOL» (правила, проверены тестами на срезе настоящих данных API)

Данные ветки: `eoasFrom` (конец активной поддержки), `eolFrom` (конец **стандартной** поддержки безопасности), `eoesFrom` (конец **расширенной** поддержки — платной, по подписке или договору), `isEol`/`isEoes`. Состояние на сегодня:

| Состояние | Когда | Критичность |
|---|---|---|
| **EOL** — поддержка закончилась | стандартная поддержка закончилась и расширенной нет либо она тоже закончилась | критическая |
| **Только расширенная поддержка** | стандартная закончилась, расширенная ещё действует | высокая, **не подтверждено**: зависит от подписки или договора (например, Ubuntu ESM, Windows ESU) |
| **Скоро** | до конца стандартной поддержки меньше `soon_days` суток (по умолчанию 180) | предупреждение |
| Поддерживается | иначе | — |
| Нет данных | в базе нет дат окончания | **EOL не присваивается** |

Принципы: даты не выдумываются; «нет данных» не равно EOL; расширенная поддержка не маскирует EOL, но и не засчитывается как подтверждённая; значения `true/false` вместо даты (так публикуют некоторые продукты) учитываются только как признак, без даты.

## Как программы и ОС сопоставляются с базой

1. **Программы.** Продукты каталога KAV Checker (его строят из реестра ПО KSC) сопоставляются с продуктами endoflife.date: по встроенной таблице (`eol/compute.py: EOL_ALIASES`), по идентификаторам CPE/PURL продукта (производитель и имя) и по названию — теми же правилами, что и сопоставление с уязвимостями (`vdb/match.py`). Уверенность: *по решению администратора* › *по идентификаторам и названию* › *только по названию*. Совпадение «только по названию» не получает критичности «критическая» (понижается до «высокой» и помечается как неподтверждённое).
2. **Ветка** выбирается по установленной версии каталога: `PHP 7.4.16 → 7.4`, `Node.js 18.20 → 18`, `Java 1.8.0_302 → 8`, `OpenSSL 1.1.1w → 1.1.1`. Версия, которой нет ни у одной ветки, EOL не получает.
3. **ОС** определяется по полям устройства KSC (название, версия, номер сборки): Windows — по номеру сборки и редакции (Pro/Home «W», Enterprise/Education «E», LTSC/IoT), Windows Server — по году выпуска, Ubuntu/Debian/RHEL и клоны — по номеру выпуска. Не определяемая ОС (например, «Linux» без версии, Astra Linux, которой нет в endoflife.date) EOL не получает. Если редакция Windows неизвестна, принята Pro/Home и добавлено пояснение.
4. **Неоднозначность.** Если подходит несколько продуктов с равной уверенностью, EOL не присваивается: запись помечается «спорной» и ждёт решения администратора («EOL → Соответствия»).
5. **Ручные соответствия** (`eol_mappings`) — «эта программа = этот продукт endoflife.date» или «не проверять EOL» — хранятся отдельно и сохраняются при обновлении базы и пересборке каталога.

## Где считается

Расчёт делает фоновая служба (worker, `eol/service.py`) под общим ограничителем ресурсов (по одной тяжёлой задаче, проверка памяти, продолжение после перезапуска): страницы читают готовые результаты (`eol_findings`, `eol_hosts`) и **не обращаются к KSC**. Пересчёт запускается сам, когда изменились база EOL, этапы поддержки веток (например, сегодня у какой-то ветки закончилась поддержка), каталог источника, решения администратора или порог «скоро»; можно запросить вручную («Пересчитать сопоставление»). При ошибке остаются прежние результаты, причина видна в разделе и в «Администрирование → EOL и пользователи». Устройства (какой компьютер какую программу или ОС имеет) читаются из KSC порциями: по записям реестра ПО выбранных версий и по полям ОС компьютеров (страницами по 20 000), в памяти — одна порция. Проверено на 20 000 компьютеров и 607 тыс. установок: см. [PERFORMANCE.md](PERFORMANCE.md).

### Состояние расчёта и надёжность (0.9.3)

* По каждому источнику показывается состояние: **Не рассчитано**, **Выполняется** (этап: «программы каталога», «устройства: программы», «устройства: операционные системы»), **Ошибка**, **Готово**, **Данные устарели** (база EOL, каталог или решения изменились после расчёта либо расчёту больше недели). Ошибка не стирает прежний результат; пока результата нет совсем, на странице вместо нулей — «—» и пояснение, а в зонах скрыта колонка EOL (`eol_missing`).
* Замена результатов источника идёт одной транзакцией под блокировкой PostgreSQL (`pg_advisory_xact_lock` по источнику) и в самом worker — не больше одного расчёта источника. Прерванный падением процесса расчёт («Выполняется» без процесса) сбрасывается при запуске worker; прежний результат цел.
* Находка EOL уникальна по (источник, продукт или ОС, версия). Одна версия продукта в каталоге может встретиться несколько раз (отдельно по схеме версий и платформе) — такие записи объединяются перед расчётом (`merge_versions`), записи реестра и устройства складываются; нарушение уникальности — ошибка расчёта с названием продукта, а не отказ базы. Причиной «duplicate key value violates unique constraint eol_findings_pkey» были повторные версии каталога и (воспроизведено тестом) два одновременных расчёта одного источника.
* Память: связи «устройство — находка» хранятся массивами `array('q')` (8 байт на связь), записи реестра читаются порциями; замеры — [PERFORMANCE.md](PERFORMANCE.md).

## Интерфейс

* **EOL → EOL в инфраструктуре**: таблица программ и ОС с критичностью, продуктом и веткой endoflife.date, состоянием поддержки (стандартная и расширенная — отдельно, дней осталось или прошло), числом устройств; фильтры по типу, состоянию, критичности, производителю, продукту, источнику (в режиме «Все источники»), зоне ответственности; раскрытие списка устройств с переходом в карточку устройства.
* **EOL → Все продукты**: вся база endoflife.date с фильтрами (поиск с `*`, категория, производитель — из CPE, «есть у нас», «все ветки завершены»), карточка продукта с датами поддержки каждой ветки.
* **EOL → Соответствия**: решения администратора, программы без соответствия и спорные.
* Экспорт: «Выгрузить» — отчёт конструктора `quick_eol` (Excel, HTML, CSV): таблица программ и ОС и **полная** таблица устройств (без «+N»).
* **Общий список проблем**: в «Уязвимости» и «База уязвимостей → Затрагивают нашу инфраструктуру» переключатель «Все / CVE / EOL»; EOL — отдельный тип и в числа CVE не входит; в дашбордах зон — отдельные счётчики «устройств с EOL» (устройство с несколькими проблемами считается один раз). «Администрирование → EOL и пользователи → Учитывать EOL в аналитике» отключает EOL в общих списках и дашбордах (раздел «EOL» остаётся).

## Таблицы PostgreSQL

`eol_products`, `eol_releases` (копия базы), `eol_mappings` (решения), `eol_findings` (результат по источнику: программа или ОС × версия), `eol_hosts` (устройства находки), `eol_state` (отпечаток исходных данных, время и ошибка расчёта). Все `eol_*` кроме `eol_mappings` — производные данные, пересчитываются.
