# Память, конкуренция и нагрузочные испытания

Документ описывает причину инцидента «worker занял всю оперативную память» (0.7.0), что изменено в алгоритмах и как это проверено на синтетической инфраструктуре крупного масштаба.

## Что происходило (разбор)

На сервере 8 ГБ ОЗУ контейнер worker за 8–9 минут после запуска занимал 7,1 ГБ (RSS около 7,4 ГБ), в PostgreSQL висел `SELECT … vdb_affected …` в состоянии `idle in transaction` больше двух минут, а в журнале регулярно были `statement timeout` цикла базы уязвимостей. Причины найдены воспроизведением на стенде и профилированием (`python -m app.tools.perf`):

| № | Где | Что делало | Измерение на стенде |
|---|---|---|---|
| 1 | `vdb/sync.analyze` (анализ уязвимостей по каталогу), запускается **при каждом старте worker для каждого источника** и при каждом изменении баз, каталога или решений | `reverse_affected` находил все уязвимости, затрагивающие любые продукты каталога, и **загружал все их записи затронутых продуктов как объекты ORM** (миллионы строк у «Windows», «Office», браузеров), держа транзакцию открытой на время сопоставления; находки читались и хранились целиком | +350…440 МБ на 6–7 тыс. находок (≈ 60 КБ на находку): при ~100 тыс. находок — около 7 ГБ; результат один и тот же при любом числе источников, но источники обрабатываются подряд, а повторный запуск после перезагрузки начинается немедленно |
| 2 | `vdb/store.upgrade_scores`, при старте | читал всю таблицу записей баз уязвимостей одной сессией — объекты копились в её карте идентичности | линейный рост с числом записей (сотни тысяч–миллионы) |
| 3 | `zones/reporter` (0.7.0) | наборы всех компьютеров, всех обнаружений и индекс «установка → потенциальные совпадения» кэшировались в процессе (рассылки, отчёты по зонам в worker) | 6,8 ГиБ RSS у worker на стенде после формирования отчётов по зонам |
| 4 | API (backend) | `analyze` вызывался прямо из запроса «добавить решение» (полный пересчёт в процессе backend); страница компьютера читала все записи по уязвимостям продуктов | рост памяти и времени запроса |

`idle in transaction`: сессия с открытой транзакцией держалась на время Python-вычислений; тайм-ауты — тяжёлый `SELECT` по `vdb_affected` без порционности (общий `statement_timeout` 120 с).

## Что изменено в алгоритмах

* **Анализ уязвимостей** читает записи порциями по 300 уязвимостей **строками, без ORM**, находки меняются и фиксируются после каждой порции, транзакция не удерживается на время вычислений. Память: **+28…35 МБ вместо +350…440 МБ** на тех же данных, результат тот же (6378 / 7522 / 7518 находок на трёх источниках), время не изменилось. Прерванный пересчёт продолжается: находки обновляются по ключу.
* **`upgrade_scores`**: только нуждающиеся записи, порциями по 500, сессия сбрасывается.
* **Решение администратора по сопоставлению** пересчитывает только затронутые уязвимости продукта (до 3000) сразу, остальное — фоновая служба по отпечатку данных; backend больше не выполняет полный пересчёт.
* **Зоны**: страницы и отчёты читают подготовленные данные PostgreSQL (см. [ZONE_CACHE.md](ZONE_CACHE.md)); расчёт — порциями в worker. Индекс потенциальных совпадений хранит не все совпадения, а **итоги и самые приоритетные записи по версиям каталога**, поэтому память не растёт с числом уязвимостей, а время — с числом совпадений у компьютера (ранее — «6000 потенциальных у каждого компьютера» превращались в гигабайты).
* **Ограничитель ресурсов** (`services/resources.py`): одна тяжёлая фоновая задача за раз (настройка 1–2), отчёты пользователей — на отдельном месте; мягкий предел памяти (50 % лимита контейнера) откладывает новые задачи, жёсткий (75 %) останавливает текущую на границе порции — она повторяется. Контейнер worker ограничен `WORKER_MEM_LIMIT` (3 ГБ, без swap), backend — `BACKEND_MEM_LIMIT` (1 ГБ). Пределы — страховка, а не замена алгоритма: в замерах ниже они не срабатывают.

## Конкуренция тяжёлых задач

До исправления в worker независимо работали циклы каталога, базы уязвимостей (загрузка и анализ), отчётов (`REPORT_CONCURRENCY=2` и каждый — на всём источнике), рассылки и расчёта зон: сразу после перезапуска все запускались вместе (анализ по каждому источнику, пересборка каталога, преобразование оценок) — ровно в те минуты, когда зафиксирован рост до 7 ГБ. Теперь:

* анализ уязвимостей, сборка каталога и расчёт зон идут под общим ограничителем (по умолчанию по одной тяжёлой задаче; «Администрирование → Расчёт данных зон» — 1 или 2), отчёты пользователей — на отдельном месте сверх этого (иначе ночной расчёт задерживал бы их на десятки минут), память проверяется при каждом входе;
* задачи, которым не хватило места или памяти, ждут в очереди либо откладываются (расчёт — на 10 минут, анализ — на 10 минут), а не запускаются вместе;
* первая тяжёлая задача после запуска всегда стартует, даже если фоновая память высока, иначе ничто не стартовало бы.

## Нагрузочные испытания

Стенд: PostgreSQL с базой уязвимостей **4,93 млн записей затронутых продуктов, 419 тыс. записей, 238 тыс. уязвимостей**; три источника KSC (синтетические, SQL Server 2022): **«нагрузочная» — 20 000 компьютеров, 607 тыс. установок ПО, около 1 млн обнаружений уязвимостей KSC**, «департаменты» — 240 компьютеров и 7 тыс. установок, малая — 8 компьютеров. Два крупных источника (по требованию «два источника, более 400 тыс. установок») — «нагрузочная» и «департаменты» вместе дают более 600 тыс. установок; результаты по первому масштабируются линейно по числу компьютеров. Запуск: сервер разработки 16 ядер / 30 ГБ (ограничения контейнеров worker 3 ГБ, backend 1 ГБ — как в поставке).

**Расчёт данных зон, полный (все три источника, 20 248 компьютеров):**

| Показатель | Значение |
|---|---|
| Длительность источника «нагрузочная» | 15,3 мин (чтение компьютеров ≈ 3 мин, поток обнаружений KSC ≈ 6 мин, индекс внешних баз ≈ 0,5 мин, потенциальные совпадения ≈ 5 мин) |
| Всего | 15,7 мин, тайм-аутов и повторов нет |
| **Пик RSS worker** | **227 МБ** (промежуточная версия со списком всех «потенциальных» совпадений компьютера на тех же данных: свыше 2,7 ГБ и остановка по жёсткому пределу; 0.7.0 — до 6,8 ГиБ) |
| Строк обнаружений сохранено | 1,85 млн (1,0 млн KSC + 0,8 млн потенциальных, не более 60 на компьютер), 1,6 ГБ с индексами |
| Размер всей базы | 5,7 ГБ (из них база уязвимостей около 4 ГБ) |
| Данные зон в резервной копии | не входят |

**Открытие страниц (API, 10 параллельных клиентов, медиана):**

| Действие | Время |
|---|---|
| Обзор зон | 108 мс |
| Зона на 17 тыс. компьютеров (сводка + 50 строк) | 406 мс |
| Зона на 2,9 тыс. компьютеров | 126 мс; малые зоны — 50–70 мс |
| Фильтры в зоне на 17 тыс.: критические / CVE / программа / поиск по имени / сортировка по IP | 499 / 451 / 259 / 246 / 304 мс |
| Карточка компьютера | 50 мс |
| 30 открытий зоны на 17 тыс. при 10 параллельных | медиана 437 мс, максимум 643 мс, всего 1,5 с |
| Память backend до и после серии | 83 → 93 МБ |

Ни одна страница не запускает расчёт и не обращается к KSC; при открытии зоны выполняется два SQL-запроса.

**Обновление одной зоны (2,9 тыс. компьютеров, источники «нагрузочная» и «департаменты»):** запрос возвращается за 29 мс, повторное нажатие дубликата не создаёт; расчёт 268 с (в том числе дважды индекс внешних баз, ожидание места), **во время расчёта 125 открытий зоны: медиана 121 мс, максимум 1,5 с**; пик памяти worker 158 МБ.

**Ночной расчёт по расписанию и перезапуск посреди него:** задание `all` запустилось само в заданное время (14:02 по Москве), через 2,5 минуты `kill -9` worker на этапе чтения обнаружений (220 тыс. из 1 млн): страницы остались доступны на прежних данных (обзор 160 мс, зона на 17 тыс. 383 мс), после запуска worker задание вернулось в очередь, недозаписанное поколение (20 тыс. компьютеров, сотни тысяч строк) удалено, расчёт повторён и завершён (вторая попытка, 15 мин), данные подменены одной транзакцией.

**Перезапуск и отказ:** `kill -9` worker посреди обновления зоны — страница продолжает отвечать прежними данными, после запуска worker задание немедленно возвращается в очередь и завершается со второй попытки, видимые данные не нарушались; недозаписанное поколение удаляется. Нехватка ресурсов: при искусственно заниженных пределах (мягкий 120 МБ, жёсткий 150 МБ) задание откладывается с понятным сообщением, процесс не падает (фрагмент журнала ниже).

**Отчёт по зоне в worker (технический, 2,9 тыс. компьютеров, 2,4 тыс. проблемных, 146 тыс. строк обнаружений KSC):** формирование документа 19 с, пик памяти +0,6 ГБ (около 4 КБ на строку: таблицы и карточки используют одни и те же строки). Предел строк одного отчёта по зонам — 300 тыс. (≈ 1,3 ГБ); сверх него отчёт отклоняется с пояснением («по меньшим зонам, в управленческом варианте или повысьте предел в настройках отчётов»). Чтение данных отчёта проверяет память и вместо аварийного завершения контейнера останавливается с понятной ошибкой.

**Анализ уязвимостей по каталогу (те же источники):** 16,8 / 22,7 / 21,3 с, пик +28 / +34 / +35 МБ (было +353 / +442 / +441 МБ).

## 0.9.0: EOL, устройства, пользователи и поиск на сотнях тысяч устройств

Что проверялось: расчёт EOL и опрос пользователей на крупных синтетических источниках KSC (SQL Server 2022, `tests/ksc_synthetic/run.sh bulk` и `bulk-lean`), а страницы — на синтетической внутренней базе **400 тыс. устройств, 1,2 млн наблюдений за пользователями и 2 млн связей «устройство — находка EOL»** (рядом с тремя обычными источниками: вместе 337 тыс. активных устройств; запуск — worker и backend в контейнерах с пределами 3 ГБ и 1 ГБ, PostgreSQL 16, тот же сервер разработки).

**Расчёт (worker, одна порция в памяти):**

| Источник | Расчёт | Время | Пик RSS worker |
|---|---|---|---|
| 20 000 компьютеров, 607 тыс. установок | EOL: находки, связи устройств, ОС | 9–13 с (70 тыс. связей, 45 находок) | 126 МБ (+56) |
| то же | опрос пользователей, 35 тыс. строк | 8–11 с | +105 МБ (порция 20 000 строк; сейчас 10 000) |
| **100 000 компьютеров, 3,05 млн установок, 177 тыс. строк пользователей** | сборка каталога (существующая функция) | 2 мин 41 с | — |
| то же | **EOL** | **46 с** (352 тыс. связей) | **172 МБ (+102)** |
| то же | **опрос пользователей** (параллельно шёл расчёт данных зон: SQL Server загружен) | 51 с | 216 МБ (+146) |

Память зависит от размера порции (записи реестра по 1 500 и ≤150 тыс. строк за запрос; компьютеры страницами по 20 000; пользователи по 10 000 строк) и от числа связей (в памяти — множества идентификаторов устройств находок), но не от числа установок. Запись связей и итогов — порциями по 5 000 строк.

**Страницы (API, 400 тыс. устройств в одном источнике и 337 тыс. активных в «Все источники»; повторный запрос, один клиент):**

| Сеть CIDR /24 · /16 | 58 · 142 мс | 196 · 49 154 |

Как это достигнуто: итоги по устройствам (`eol_host_stat`: число проблем, критических, наихудшее состояние, активность) считаются при расчёте и читаются готовыми; страница устройств берёт «первые N строк каждого источника» по индексам (`ix_zc_hosts_lname`, `ix_zc_hosts_ip`, частичный `ix_zc_hosts_active` для числа активных) и объединяет их; адреса — диапазоны чисел; имя и логин — триграммные индексы (`pg_trgm`); итоги EOL и пользователи читаются только для устройств страницы. До этого запрос первой страницы на тех же данных занимал 8 секунд (агрегаты по миллионам связей при каждом открытии).

Повтор: `python -m app.tools.perf eol|users --source "…"` (расчёт и опрос с замером памяти), `tests/ksc_synthetic/run.sh bulk-lean 100000 KAVHUGE` (крупная база без уязвимостей и событий). Тесты новых модулей запускаются и на PostgreSQL: `TEST_PG_URL=postgresql+asyncpg://postgres:пароль@127.0.0.1:5432/postgres pytest …` (каждый тест — отдельная база).

## 0.9.3: EOL, отчёты, база уязвимостей и наблюдаемость

Замеры на синтетических источниках (SQL Server 2022 в Docker) и внутренней базе PostgreSQL с реальным объёмом базы уязвимостей (4,93 млн записей затронутых продуктов). **Данных рабочих источников у разработки нет — проверка на них остаётся за установкой** (команды ниже).

| Операция | Было | Стало | Примечание |
|---|---|---|---|
| Расчёт EOL, 20 тыс. устройств (`perf eol`) | 9 с, +57 МБ | 9 с, +57 МБ | без изменений по времени; ошибка дубля ключа исправлена |
| Расчёт EOL, 100 тыс. устройств, 352 тыс. связей | 42,5 с, +102 МБ | 41 с, +90 МБ | связи — массивами `array('q')` вместо множеств |
| XLSX отчёта, 100 тыс. строк × 19 столбцов | пик 1048 МБ, 65 с | пик 234 МБ, 65 с | потоковая запись (`reports/xlsx.py`); память не зависит от числа строк |
| Анализ находок источника (`analyze`), 4,9 млн записей | 25 с, +35 МБ | 22–29 с, ≈105 МБ | дополнительно строится таблица «находка × продукт» (8–9 тыс. строк на источник) |
| План устранения, сводка, фильтры по категории/достоверности/EOL | — | 0,09–0,4 с | агрегаты SQL по индексированной таблице |
| Страница «Уязвимости KSC» (крупный источник) | ожидание запроса при каждом истечении кэша | устаревшие данные сразу, обновление в фоне | `CACHE_SWR_SECONDS` (по умолчанию 3600) |

Что проверено и отвергнуто: один запрос `GROUPING SETS` вместо двух агрегатов списка уязвимостей KSC оказался в шесть раз медленнее (38 с против 6+7 с на 650 тыс. обнаружений): запросы идут параллельно. Замер через `SELECT COUNT(*) FROM (…)` обманчив — оптимизатор отбрасывает неиспользуемые столбцы; замеряйте запрос целиком.

PostgreSQL: настройки по умолчанию (`shared_buffers` 128 МБ, `work_mem` 4 МБ) заменены значениями в `deployment/compose.yml` (переменные `PG_*`, лимит `POSTGRES_MEM_LIMIT`), подключение worker — отдельный `statement_timeout` (30 мин) и `application_name`, `lock_timeout` 60 с, `idle_in_transaction_session_timeout` (страницы 5 мин, worker 15 мин). Планы запросов страниц чтения проверены на таблицах 0,5–4,9 млн строк: полных сканирований больших таблиц на частых запросах нет, медленнее 0,5 с — только агрегаты зон по всем источникам (0,4 с).

Известное ограничение, не устранённое в 0.9.3: страницы «Состояние защиты» и «Уязвимости» читают KSC напрямую и держат результат в памяти backend (на 100 тыс. устройств — около 180 МБ на источник, холодный запрос 15 с). На источниках свыше 200 тыс. устройств им нужен перенос на подготовленные данные (как у зон, EOL и устройств).

## Как повторить

```bash
# профиль памяти анализа и сборки каталога на данных установки (внутри контейнера worker; изменения не фиксируются)
docker compose exec worker python -m app.tools.perf analyze
docker compose exec worker python -m app.tools.perf catalog --source "…"
# время открытия страниц зон (на работающей установке)
python3 tests/perf/dash_load.py http://127.0.0.1:18080 admin 'пароль' 10
# память worker за время расчёта: «Администрирование → Расчёт данных зон» (пик в блоке «Память фоновой службы») или docker stats
# 0.9.3: проверка на рабочих источниках — только чтение KSC; «eol» и «users» записывают результат во внутреннюю базу, как обычный расчёт
docker compose exec worker python -m app.tools.perf eol --source "kav01"          # время, пик памяти, число находок и связей
docker compose exec worker python -m app.tools.perf analyze --source "kav01"      # анализ находок и строк «находка × продукт»
# медленные запросы PostgreSQL (порог PG_LOG_SLOW_MS, по умолчанию 2 с)
docker compose logs postgres | grep "duration:"
# долгие транзакции и соединения
docker compose exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select state, count(*), max(now()-xact_start) from pg_stat_activity group by 1"
```
