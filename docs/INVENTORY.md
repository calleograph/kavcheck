# Инвентаризация (учёт ИТ-активов)

Раздел «Инвентаризация» (`/inventory`) — второй контур KAV Checker. Технический аудит и безопасность, как и раньше, опираются на KSC. Инвентаризация добавляет **учётную составляющую** имущества:

- инвентарные номера и принадлежность;
- местоположение и движение;
- ответственных лиц;
- документы (акты, перемещения, ремонты, списание);
- лицензии;
- историю на протяжении всего срока службы.

Технические сведения второй раз не собираются. Процессор, память, накопители, сеть, установленное ПО, владелец по BI и состояние защиты берутся из уже имеющихся данных KAV Checker. Для этого учётная карточка связывается с компьютером KSC. Данные KSC только читаются: изменение учётных полей источники не затрагивает.

## Где что находится

| Раздел | Что в нём |
|---|---|
| Обзор | состав и состояние, учётная стоимость, связь с KSC, «Требует внимания» (каждое число открывает список), незавершённые документы, последние изменения |
| Оборудование | реестр с поиском по всем полям и свойствам, фильтрами, сохранёнными фильтрами, группировкой, массовыми операциями, созданием карточек из KSC, этикетками и отчётом по выборке |
| Карточка | вкладки: учётные сведения, расположение и ответственные, техника (KSC), ПО и лицензии, состав и связи, документы, история (и состояние на дату), вложения |
| Документы | выдача, возврат, перемещение, приём-передача, передача МЦ, приём неисправного, ремонт, списание, работы; этапы и печатные формы (в приложении, PDF, DOCX, HTML) |
| Местоположения | дерево «регион → город → адрес → здание → этаж → помещение → рабочее место», площадки, серверные, стойки, склады; число единиц в узле и поддереве; этикетки помещений |
| Сотрудники | сотрудники учёта (вручную, из BI, из адресной книги); закреплённое оборудование по ролям, история закреплений, возврат или снятие ролей при увольнении |
| Лицензии | купленные лицензии: количество, срок, назначения, установки по данным KSC, расхождения; ключ активации хранится зашифрованным |
| Отчёты | каталог отчётов с отбором и периодом |
| Сканирование | камера телефона или ручной сканер: QR, штрихкод, инвентарный или серийный номер ведут в карточку |
| Справочники | типы, производители и модели (со значениями свойств по умолчанию), статусы, поставщики и сервисные организации, подразделения, филиалы, типы лицензий, категории программ, дополнительные свойства |
| Импорт | Excel или CSV: сопоставление столбцов, проверка без записи, импорт с отчётом об ошибках |
| Настройки | права по ролям и учётным записям, области учёта, нумерация, печатные формы, этикетки, сроки контроля (только администратор) |

В карточке компьютера («Компьютеры» → компьютер) есть блок «Инвентаризация». В нём показаны инвентарный номер, категория и статус, местоположение, пользователь и владелец, ответственный и МОЛ, дата изменения учётных сведений и ссылка на учётную карточку. Если связи нет, блок предлагает карточки с тем же именем для сопоставления или создание новой карточки.

## Модель данных

| Таблица | Назначение |
|---|---|
| `inv_assets` | Учётная единица. Хранит: `uid` для QR, инвентарный и бухгалтерский номера, серийный номер, тип, модель, статус, местоположение, пять ролей сотрудников, приобретение и гарантию, стоимость в копейках, `props` (дополнительные свойства), связь с KSC (`ksc_source_id` + `ksc_host_id`, состояние `confirmed` / `auto` / `lost`), `parent_id` (состав, ВМ на хосте, подключение), `ext_ids` (идентификаторы других систем), `version` (защита от одновременной правки) |
| `inv_history` | Событие истории: изменения «было → стало», состояние **после** события (по нему строится «состояние на дату»), основание, документ, участвовавшие сотрудники |
| `inv_locations` | Дерево местоположений. `path` — полный путь, `ids_path` — выборка поддерева одним условием |
| `inv_refs` | Справочники. У типа есть класс, у статуса — состояние учёта, модель привязана к производителю и может хранить значения свойств по умолчанию |
| `inv_props` | Определения дополнительных свойств: тип, варианты, значение по умолчанию, обязательность, типы оборудования, показ в списке |
| `inv_people` | Сотрудники учёта; `source` и `ext_key` — откуда перенесён сотрудник (BI, адресная книга) |
| `inv_docs`, `inv_doc_items` | Документы и их строки. Строка хранит сведения единицы на момент оформления (`snap`) |
| `inv_licenses`, `inv_lic_assign` | Лицензии, назначения единицам и сотрудникам, последний подсчёт установок (`usage`) |
| `inv_files` | Вложения до 15 МБ. Хранятся в базе, поэтому попадают в резервные копии |
| `inv_views` | Сохранённые фильтры, личные или общие |

Миграция — `0035_inventory`. Расширение карточки делается дополнительными свойствами и справочниками, без новых столбцов. Чтобы добавить тип оборудования, менять схему не нужно.

**Классы** (фиксированы, на них опираются правила): рабочая станция, ноутбук, физический сервер, виртуальный сервер, монитор, принтер и МФУ, сетевое оборудование, СХД, периферия, комплектующее, прочее. **Состояния учёта** (тоже фиксированы): на складе, в эксплуатации, зарезервировано, в ремонте, списано, выведено из эксплуатации, утрачено. Типы и статусы — справочники администратора, у каждого указан класс или состояние.

## Правила

- **История — у каждого изменения.** Создание, правка, массовая операция, документ, импорт, связь с KSC, вложения и лицензии записываются событием карточки. В событии есть кто и когда, «было → стало», основание и ссылка на документ. В журнал действий (`inv.*`) пишется сама операция. Карточки не удаляются: списание и вывод из эксплуатации — это статусы.
- **Состояние на дату** берётся из последнего события не позже этой даты. Каждое событие хранит учётное состояние после себя: статус, местоположение, пять ролей, подразделение.
- **Одновременная правка.** Если карточку уже изменил другой пользователь, сохранение отклоняется со ссылкой на автора. Перед повтором нужно обновить страницу.
- **Документы меняют карточки на «своём» этапе:**
  - перемещение: «Отправлен» ставит отметку «в пути», «Принят» записывает новое местоположение и ответственных;
  - ремонт: «Отправлен» ставит статус «В ремонте» и запоминает прежний, «Завершён» возвращает прежний;
  - остальные документы меняют карточки при проведении.
  Единица «в пути» не попадает в другое перемещение, выдачу или возврат. Списанное нельзя выдать.
- **Связь с KSC.**
  - Устойчивый ключ связи — «источник + идентификатор компьютера KSC». Создание карточек из KSC и повторный импорт не порождают дублей: эта пара уникальна.
  - Имя компьютера только **предлагает** связь, когда оно совпало ровно с одним компьютером всех источников. Такая связь получает состояние «предполагается», и её подтверждает пользователь.
  - Если компьютер исчез из KSC, связь отмечается «нет в KSC», а карточка сохраняется. Сверку раз в 15 минут выполняет worker по подготовленным данным, сам KSC при этом не опрашивается.
  - Расхождения серийного номера и имени между карточкой и KSC показываются, но автоматически не исправляются.
- **Область учёта.** Учётной записи можно ограничить видимость поддеревьями местоположений: «Настройки → Права доступа». Такой пользователь видит и меняет только оборудование в разрешённых местах. Отчёты строятся по его области: сервер подставляет её сам, параметр клиента игнорируется.
- **Ключи лицензий** шифруются ключом `APP_MASTER_KEY`. В списки, карточки и отчёты ключи не попадают. Ключ выдаётся отдельным запросом с правом «просмотр ключей лицензий», и каждое открытие пишется в журнал действий.

## Права

Право даётся по наименьшей роли (настраивается). Сверх роли учётной записи можно выдать отдельные права.

| Право | По умолчанию |
|---|---|
| просмотр оборудования | просмотр |
| создание карточек; изменение учётных свойств; изменение местоположения; изменение владельцев и ответственных; оформление документов; оформление ремонтов; инвентаризация; импорт | аналитик |
| просмотр ключей лицензий | специалист по ИБ |
| списание; справочники и местоположения; печатные формы и этикетки | администратор |

Выгрузка отчётов, как и во всём KAV Checker, доступна начиная с аналитика. Ответственному за зону раздел недоступен.

## Отчёты

Вид отчёта — `quick_inv`. Отчёт строится по тем же параметрам отбора, что и список. Если строки выбраны флажками, отчёт строится по ним. Форматы — XLSX, CSV, PDF, HTML. В HTML логические части разложены по вкладкам, в XLSX — по отдельным листам.

| Вид | Содержание |
|---|---|
| `registry`, `computers` | реестр ИТ-оборудования; реестр компьютеров и серверов (имя, ответственные, связь с KSC) |
| `card` | карточка единицы: учётные сведения, свойства, состав, документы, история, лицензии |
| `by_person`, `by_resp` | оборудование по сотрудникам (любая роль) и по ответственным |
| `by_location` | состав по местоположениям |
| `stock`, `repair`, `warranty`, `writtenoff`, `cost` | склад и резерв; ремонт с открытыми ремонтами; истекающая гарантия; списанное; стоимость по типам, местоположениям, подразделениям |
| `owner_history`, `moves` | история принадлежности и история перемещений за период |
| `hardware`, `software` | аппаратная конфигурация и установленное ПО связанных компьютеров (из KSC, группами) |
| `licenses`, `license_usage` | реестр лицензий; куплено, назначено, установлено, расхождения |
| `components`, `docs`, `duplicates` | состав и комплектующие; журнал документов; возможные дубли (совпадение серийного номера или имени) |

**Печатные формы документов** — акт выдачи, акт возврата, акт внутреннего перемещения, акт приёма-передачи, акт передачи материальных ценностей, акт приёма неисправного оборудования, направление в ремонт, акт списания, наряд на работы.

- В форме только сведения документа: номер и дата, стороны, основание, таблица оборудования, места для подписей. Технических полей KSC в актах нет.
- Шапка формы берётся из «Организация и отчёты».
- Настраиваются заголовок, вводный текст с подстановками, столбцы, дополнительные свойства в таблице, подписи и заключительный текст.
- Форма открывается в приложении (лист A4, печать из браузера) и скачивается как PDF, DOCX (для правки) и HTML.

**Этикетки:**

- PDF: страница на этикетку для принтера этикеток или лист A4 с сеткой для клеящейся бумаги;
- ZPL для принтеров Zebra;
- код — QR со ссылкой на карточку (камера телефона открывает её сразу), штрихкод Code 128 с инвентарным номером, или оба;
- этикетка помещения несёт код `LOC:<id>` для будущей инвентаризации со сканированием.

## Импорт Excel / CSV

- Первая строка файла — заголовки. Столбцы сопоставляются с полями по названиям, сопоставление можно поправить вручную.
- Совпадение с существующей карточкой ищется по инвентарному номеру, затем по однозначному серийному номеру.
- Режимы:
  - «только новые»;
  - «новые и обновление» — меняются только сопоставленные столбцы, пустая ячейка значение не стирает.
- Отсутствующие значения справочников, местоположения (по пути «А / Б / В») и сотрудники (по почте или ФИО) создаются, если это разрешено. Классы типов и состояния статусов автоматически не создаются.
- «Проверить» показывает, сколько карточек будет создано и изменено, и ошибки по строкам; в базу ничего не записывается. Импорт выполняется построчно: строка с ошибкой пропускается и попадает в отчёт.
- Повторная загрузка того же файла дублей не создаёт.
- Ограничения: до 20 000 строк и 30 МБ на файл.

**Обязательный формат результата каждого этапа:**

1. **Выпуск на GitHub** с журналом изменений «для пользователя». Установка обновляется штатно: «Администрирование → Обновления». Миграция базы — только добавление таблиц и столбцов.
2. **Работающий сценарий от начала до конца** в интерфейсе. Это не заготовка: страницы, API, права, история и журнал действий.
3. **Отчётность:** кнопка отчёта на каждой новой странице с данными, виды `quick_inv` для новых списков, печатные формы для новых документов.
4. **Проверки:**
   - модульные тесты на правила этапа: права, история, отсутствие дублей, применение на этапе;
   - полный прогон тестов;
   - сборка интерфейса;
   - `check_private_data.py`.
5. **Проверка в браузере** на стенде:
   - сценарии этапа;
   - снимки на ширинах 320, 390, 768, 1024, 1280, 1440 и 1920;
   - аудит компоновки на этих ширинах.
6. **Документация:** этот файл (раздел этапа), `FUNCTION_MAP.md`, при необходимости `ADMIN_GUIDE.md`.
7. **Отчёт владельцу:** что сделано, что проверено и как, что не проверено и почему, что изменилось в правах и данных.

Ориентир — IT Invent: изучены справка (83 страницы), описание функций, история версий и подписи скриншотов. Это толстый клиент под Windows с прямым доступом к базе: без веб-интерфейса, мобильного клиента и API. Местоположения в нём плоские, разграничение доступа только по компании и филиалу. ## Серверная и сетевая инфраструктура: решение и план (этап 4)

Задача — единое достоверное представление о серверах, ВМ, гипервизорах, кластерах, сетевом оборудовании, IP-адресах, подсетях и VLAN, площадках и стойках, внешних ресурсах, сервисах. Технические сведения должны поступать автоматически, а основная работа людей — сводиться к разбору исключений.

### NetBox, Nautobot или своё (сравнение вариантов)

| Критерий | А. Реестр в KAV Checker | Б. NetBox — основа, KAV Checker — интерфейс аудита | В. Nautobot + SSoT |
|---|---|---|---|
| Полнота | только то, что сделаем; стойки и кабели — дорого | лучшая модель DCIM/IPAM; учёта имущества нет (только плагины) | как NetBox, плюс гибкие связи и Jobs |
| Zabbix | прямое чтение API (нужно для сверки в любом варианте) | плагины только в сторону NetBox → Zabbix | готового нет |
| vSphere / Proxmox / Hyper-V, oVirt (zVirt) | свои коллекторы (API простые) | netbox-sync (сторонний), proxbox (0.0.x); Hyper-V и oVirt — нет | vSphere (одностороннее); Proxmox, Hyper-V, oVirt — нет |
| Права | единые роли и области KAV Checker | вторая модель прав, её надо синхронизировать | так же |
| Сопровождение | в нашем цикле выпусков, одна база | ещё PostgreSQL, Redis, воркеры, выпуски каждые 2 недели, совместимость плагинов | тяжелее Б: Celery, Git, ломающие изменения 3.x |
| Своя разработка | высокая на модель и интерфейс | средняя: клиент API, сопоставление, права | средняя или высокая: задания на Python внутри Nautobot |
| Резервирование | уже есть (`scripts/`) | ещё одна база и медиафайлы | то же плюс Git |
| Стоимость | разработка | бесплатно + администрирование; Discovery, Assurance, SSO — платно | бесплатно + администрирование |

**Рекомендация — вариант А в узких рамках, с коннектором NetBox (или Nautobot) на чтение, если такая система уже ведётся.**

- Ценность KAV Checker — в **сверке** источников. Реестру инфраструктуры нужны:
  - объекты (хост, ВМ, кластер, сетевое устройство, IP и подсеть, площадка или стойка);
  - идентификаторы;
  - атрибуты с источником и датой;
  - расхождения с решениями.
  Это несколько таблиц и коллекторов. Полноценная DCIM для этого не нужна.
- NetBox и Nautobot не закрывают главного: чтения из Zabbix, Hyper-V и oVirt/zVirt. Proxmox у них поддерживается только пакетом версии 0.0.x, разграничения по нашим областям нет. Мы получили бы вторую систему прав, вторую базу, второй цикл обновлений и двойной ввод.
- Если NetBox (или Nautobot) уже ведётся, он подключается как **ещё один источник**: устройства, ВМ, IP, VLAN и размещение читаются по API токеном и участвуют в сверке.
- Пилот NetBox и Nautobot на одном наборе объектов проводится перед этапом 4, если заказчик решит вести DCIM во внешней системе. Сценарии пилота перечислены в постановке.

### Модель этапа 4

- **Источники** (`inv_sources`): Zabbix, vSphere, Proxmox, Hyper-V (WinRM, только чтение) и oVirt/zVirt, NetBox или Nautobot, API провайдеров, KSC (уже есть).
  - У каждого источника: адрес, тип, секрет (зашифрованно), проверка соединения с показом найденных объектов, расписание, последняя успешная синхронизация, ошибки, число полученных и изменённых объектов.
  - Ошибка одного источника не останавливает остальные: каждый собирается своим заданием под арендой.
- **Наблюдения** (`inv_observations`): объект источника с устойчивым идентификатором и атрибутами на момент синхронизации. История — по изменениям.
- **Сопоставление** с учётной единицей, по убыванию надёжности:
  1. SMBIOS UUID (с проверкой обоих порядков байт: у VMware первые три группы перевёрнуты относительно Windows и Linux);
  2. серийный номер;
  3. внутренний идентификатор системы;
  4. MAC;
  5. FQDN, имя, IP — только как подтверждающий признак.
  Неоднозначное сопоставление решается вручную. Повторная синхронизация обновляет существующее. Исчезновение объекта — это «требует проверки», а не удаление.
- **Приоритет источников по атрибуту** (матрица в настройках):
  - CPU, RAM, диски, состояние ВМ — система виртуализации;
  - доступность и наличие в мониторинге — Zabbix;
  - IP, подсети, VLAN — IPAM (NetBox или утверждённый источник);
  - размещение — инвентаризация или DCIM;
  - назначение и ответственный — учёт;
  - антивирусная защита — KSC;
  - резервное копирование — система резервного копирования.
  По каждому атрибуту хранятся значение, источник, время и актуальность. Конфликт показывается и разрешается по правилам.
- **Сверка** (`inv_findings`) с решениями «требует внимания / проверки / подтверждено / исправляется / устранено / исключение», как в аудите домена. Что выявляется:
  - объект есть в виртуализации, но нет в реестре;
  - объект есть в реестре, но нет в Zabbix (и наоборот);
  - изменился IP; один IP у нескольких объектов;
  - ВМ числится на старом хосте;
  - устаревшие сведения;
  - нет резервного копирования, мониторинга, ответственного или назначения;
  - конфигурация отличается от учётной;
  - выведенный объект остался в мониторинге.
- **Жизненный цикл.** Новый объект проверяется:
  - именование;
  - сеть;
  - ответственный, назначение и сервис;
  - мониторинг, резервное копирование, защита;
  - площадка.
  Вывод из эксплуатации оформляется документом с проверочным списком. Действия во внешних системах — только подтверждаемыми операциями с журналом; по умолчанию раздел только читает.
- **Обзор инфраструктуры** с показателями и отчёты:
  - реестры;
  - IP и подсети;
  - стойки (визуальная карта юнитов);
  - объекты без мониторинга, резервного копирования, ответственных;
  - расхождения, изменения конфигурации, новые и исчезнувшие объекты;
  - синхронизация;
  - вывод из эксплуатации;
  - состояние на дату;
  - полугодовая проверка.

Модель этапа 1 к этому готова: класс «виртуальный сервер», связь «ВМ на хосте» (`parent_id`, `rel = vm`), `ext_ids` для идентификаторов других систем, стойки и серверные в местоположениях.

## Для разработчиков

- `backend/app/inventory/`:
  - `model.py` — словари: классы, состояния, виды, формы по умолчанию, встроенные справочники;
  - `core.py` — права и область учёта, номера, проверка и применение изменений, история, имена, вывод карточки;
  - `query.py` — отбор реестра (общий для списка, группировки, массовых операций и отчётов);
  - `docs.py` — этапы документов;
  - `printing.py` — печатные формы (структура, HTML, PDF, DOCX без внешних библиотек);
  - `labels.py` — этикетки PDF и ZPL;
  - `importer.py` — Excel и CSV;
  - `service.py` — worker: сверка связей с KSC, подсчёт использования лицензий.
- API:
  - `api/inv.py` — реестр, карточка, история, связь с KSC, сохранённые фильтры, вложения, импорт;

  - `api/inv_docs.py` — документы, печать, этикетки;
  - `api/inv_lic.py` — лицензии.
- Отчёт — `reports/quick_inv.py`. Настройки — группа `inventory` (`InventorySettings`). Запрос к KSC для лицензий — `queries.LIC_HOSTS`.
- Интерфейс — `frontend/src/pages/inventory/`: оболочка `InvApp.tsx` и навигация `INV_NAV` в `navModel.ts`. Блок в карточке компьютера — `components/InvHostBlock.tsx`.
- Тесты — `tests/test_inventory.py`.
