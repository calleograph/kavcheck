# Алгоритмы обработки данных KSC

Эталонная реализация — `backend/app/ksc/versions.py`, `grouping.py`, `hosts.py`; тесты — `backend/tests/test_versions.py`, `test_activity.py`.

## 1. Сравнение версий

Версии хранятся строками; строковое сравнение неверно (`8.10` < `8.9`). Используется алгоритм dpkg: `эпоха:upstream-ревизия`; части сравниваются поочерёдно — нецифровой префикс посимвольно (`~` меньше конца строки, буквы раньше прочих символов), затем число как число.

Проверочные пары (левая меньше): `8.9` < `8.10`; `1.0~rc1` < `1.0`; `2.0` < `1:0.1`; `7.1.33-2+0~2019` < `7.1.33-14+0~2020`; `120.0.6099.130` < `120.0.6099.200`.

`upstream(v)` — без эпохи и ревизии: `2:8.1+92ubuntu1` → `8.1+92ubuntu1`; `7.1.33-14+0~2020…` → `7.1.33`.

Диапазон «7.x»: `compare(v, "7") >= 0 and compare(v, "8") < 0`. Граница `7.99` неверна: пропускает `7.100`.

Для RPM отличия `rpmvercmp` (буквы против цифр, `^`) не учтены.

## 2. Ветка продукта и версия пакета (PHP и аналоги)

- `phpX.Y-*` (Debian) и `php`, `php-cli`, `php-common` (RPM): версия пакета ≈ версия продукта (`7.1.33-14+…` → 7.1.33).
- `php-common 2:70+…`, `php-xml 2:7.3+70` (Debian): метапакеты, версия — ветка дистрибутива; ветку по ним определять нельзя (`2:70+…`), либо она равна `7.3`.
- `php-pecl-*`, `php-symfony-*`, PhpStorm, Composer, WinCache — не PHP, в группу не входят.
- Пакеты с веткой в имени (`php7.4-xdebug`, `libapache2-mod-php8.1`, `php74-php-cli`, `rh-php73`) несут версию **расширения**: сравниваемая версия = ветка из имени, если версия пакета не начинается с неё.

Отбор пакетов ядра PHP (регистр не важен):

```
^(php[0-9]+\.[0-9]+(-.+)?|php(-(cli|common|fpm|cgi))?|libapache2-mod-php[0-9.]*|php[0-9]+-php(-.+)?|rh-php[0-9]+(-php(-.+)?)?|PHP [0-9].*)$
```

Первичный отбор в базе — `LIKE '%php%'` (на сортировке `_CI_` шаблон `'php%'` захватил бы PhpStorm), затем регулярное выражение в приложении. Ветка = первые две числовые части сравниваемой версии; если их нет — «не определена». Правило обобщено в `grouping.Rule` (LIKE, регулярное выражение имени, регулярное выражение ветки из имени, число частей ветки, исключения) — так добавляются другие продукты.

## 3. Чтение больших выборок

Страницы `ORDER BY … OFFSET … FETCH`, установки пачками `nProduct IN (…)` по 300, устройства `nId IN (…)` по 500. Предел строк отчёта и флаг отмены проверяются между пачками. Это не согласованный снимок: таблицы читаются в разные моменты.

## 4. Путь группы администрирования

Все группы читаются одним запросом (`GROUPS_ALL`), путь собирается подъёмом по `nParentId` до группы без известного родителя, имена соединяются « / ». Рекурсивный CTE не используется (на производственной базе лучше один лёгкий запрос).

## 5. IP-адрес

`nIp` — целое, первый октет в старшем байте: `a = n >> 24 & 255`, `b = n >> 16 & 255`, `c = n >> 8 & 255`, `d = n & 255`. Пустое или 0 — адреса нет.

## 6. Статус активности

Порог по `GETUTCDATE() - tmLastNagentConnected`: ≤1, ≤3, ≤7, ≤14, ≤30 суток, дольше; NULL — Агент не подключался. По умолчанию актуальны устройства за 7 суток (настройка). Статус KSC (биты `nStatus`, `v_akpub_host_status`) — отдельный признак. В отчётах всегда указывается, сколько устройств исключено по порогу.

## 7. Защита базы KSC

Только SELECT/WITH (проверка `guard.py` до подключения), параметры через драйвер, `READ UNCOMMITTED` и `LOCK_TIMEOUT 5000` на соединении, тайм-аут запроса, предел строк, семафор одновременных запросов на источник, учётная запись `db_datareader`. Диагностика предупреждает, если у учётной записи есть права на запись.
