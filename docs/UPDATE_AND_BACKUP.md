# Обновление, откат, резервное копирование

## Как устроено

Релизы публикуются в GitHub: тег `vX.Y.Z`, страница релиза с описанием из CHANGELOG и образы `ghcr.io/<владелец>/kavcheck-backend:vX.Y.Z`, `…-web:vX.Y.Z`. Все установки обновляются из одного источника релизов, сохраняя свои `.env`, внутреннюю базу, отчёты и подключения.

Контейнер backend не имеет доступа к Docker и git сервера. Обновление из браузера выполняет **помощник** — служба systemd `kavcheck-updater-<проект>` на сервере (`scripts/updater.sh`), которая читает запросы из каталога `DATA_ROOT/updater` и выполняет только фиксированный набор действий: проверка релизов, проверки перед обновлением, обновление, откат, резервная копия, восстановление копии, сбор сведений о дисках и образах. Произвольные команды из веб-интерфейса выполнить нельзя.

## Обновление

**Основной способ — готовые образы.** Для каждого релиза CI публикует образы `ghcr.io/<владелец>/kavcheck-backend|web:vX.Y.Z`. Обновление скачивает именно их: Docker Hub, npm и pip не нужны, занимает минуты. Репозиторий образов берётся из `IMAGE_REGISTRY`, иначе проверяются по порядку `GITHUB_REPO` и адрес `origin` — используется первый, где образ релиза опубликован; значение `IMAGE_REPO=kavcheck` в `.env` (образы, собранные при установке из исходников) на выбор способа не влияет. **Локальная сборка** запускается только по явному решению: кнопка «Собрать локально» (с отдельным подтверждением), `scripts/update.sh --build`, `UPDATE_MODE=build` или `UPDATE_ALLOW_BUILD=1` в `.env` (тогда при недоступных образах сборка включается автоматически, с предупреждением в журнале). Без этого при недоступном реестре обновление останавливается, работает прежняя версия, а интерфейс объясняет причину и предлагает действия.

В браузере: Администрирование → Обновления → «Проверить релизы» → при необходимости «Проверить» в блоке «Проверки перед обновлением» → «Обновить до X.Y.Z». Показываются реальный этап, длительность, время последнего вывода и журнал; зависший шаг помечается предупреждением. Если обновление остановилось, красная плашка сразу называет причину (Docker Hub, реестр образов, образов нет, npm, pip, сеть, диск, сборка, миграция, проверка работоспособности, тайм-аут, прерывание), даёт совет и кнопки «Скачать журнал», «Собрать локально» (если применимо) и «Повторить». **«Скачать журнал»** отдаёт файл с итогом, причиной, проверками и полным журналом последнего обновления для диагностики (пароли и учётные данные в адресах зеркал маскируются; предыдущий журнал — `?which=prev`).

На сервере:

```bash
./scripts/update.sh            # до последнего релиза, из готовых образов
./scripts/update.sh --to v0.2.0
./scripts/update.sh --build    # явная локальная сборка (нужны Docker Hub, npm, pip или их зеркала)
./scripts/update.sh --dry-run  # только проверки, ничего не меняется
./scripts/recover.sh           # проверить и восстановить состояние после прерванного обновления
```

Шаги `scripts/update.sh` (11):

1. Текущая версия и способ получения образов.
2. Получение тегов из GitHub, выбор релиза.
3. Проверки перед обновлением — по **фактически используемым** источникам: для готовых образов — реестр (`ghcr.io`) и наличие манифеста релиза; для сборки — реестр npm и индекс pip (с учётом зеркал), Docker Hub, если базовых образов нет на сервере; в обоих случаях — место на дисках, доступ к GitHub, работа внутренней базы и ревизия, образы текущей версии для отката. Не пройдены — ничего не меняется.
4. Переход кода на тег релиза. Локальные правки зеркал в файлах проекта переносятся в `.env`, сами правки сохраняются в `DATA_ROOT/state/local-changes-*.patch`; прочие правки откладываются в `git stash`.
5. Образы: загрузка (или сборка).
6. Остановка backend и worker, резервная копия внутренней базы и `.env` (хранятся последние 14 копий базы; копий `.env` перед обновлением — 5). После копии в базу никто не пишет — возврат к ней не теряет данных.
7. Миграции Alembic.
8. Запуск и проверка: healthcheck, `/api/v1/health/ready`, версия.
9. Очистка: остаются образы **текущей и предыдущей** версии (откат на один релиз); прочие образы проекта удаляются только после успешной проверки новой версии. Единственные рабочие образы не удаляются никогда.
10. Помощник: файл службы приводится к версии релиза; сам помощник перезапускается на новом коде в паузе между действиями.
11. Отчёт `DATA_ROOT/updater/report.json` (итог, причина, совет, действия) и запись в истории.

### Тайм-ауты и контроль прогресса

У каждой операции своё ограничение (секунды; переопределяются в `.env`): сетевые проверки `UPD_TIMEOUT_NET` (60), загрузка образов `UPD_TIMEOUT_PULL` (1800) и `UPD_STALL_PULL` (300 — нет вывода), сборка `UPD_TIMEOUT_BUILD` (2400) и `UPD_STALL_BUILD` (900), резервная копия `UPD_TIMEOUT_BACKUP` (900), миграции `UPD_TIMEOUT_MIGRATE` (600), запуск сервисов `UPD_TIMEOUT_UP` (300), проверка здоровья `UPD_WAIT_HEALTH` (180). Превышение времени или отсутствие вывода дольше «нет прогресса» останавливает операцию вместе со всеми дочерними процессами (TERM, затем KILL; оставшиеся разовые контейнеры `compose run` удаляются). Над этим — общий сторож помощника: `UPD_TIMEOUT_TOTAL` (5400) и `UPD_STALL_TOTAL` (1500, нет вывода в журнале). Блокировка обновления (`DATA_ROOT/state/update.lock`) снимается операционной системой при завершении процесса, одновременно может идти только одно обновление, откат или восстановление.

### Если обновление остановилось или было прервано

* **Ошибка или зависание на любом этапе** — обновление само возвращает прежнюю версию по этапу из метки `DATA_ROOT/state/update.inprogress`: до остановки контейнеров — возвращаются код и `.env`; после остановки приложения, но до миграции — запускается прежняя версия; при ошибке или прерывании миграции и при непрошедшей проверке здоровья — база восстанавливается из копии шага 6 в чистую базу (неудачная сохраняется как `<база>_failed_<время>`) и запускается прежняя версия. Причина и совет — в отчёте и журнале.
* **Перезагрузка сервера, остановка помощника, kill процесса** — при старте помощник читает метку и запускает `scripts/recover.sh`: проверяет фактическое состояние и возвращает работоспособную версию. Если новая версия уже работала и прошла проверку, она остаётся (данные не откатываются, чтобы не потерять записанное после запуска); если не успела заработать — база возвращается к копии, запускается прежняя. Если безопасно решить нельзя, автоматически ничего не делается: отчёт содержит команды для ручного восстановления. **Повторное обновление автоматически не запускается.** Статус «Выполняется» от прежнего процесса снимается: интерфейс показывает «прервано» и результат восстановления.
* `scripts/update.sh`, запущенный вручную, перед началом сам обрабатывает прерванное предыдущее обновление.

### Помощник обновлений

Служба systemd `kavcheck-updater-<проект>`: `Restart=always`, `RestartSec=10`, без предела числа перезапусков, `KillMode=control-group` (при остановке завершаются и дочерние процессы), включена в автозапуск. Её устанавливает `scripts/install.sh` (запуск от root); повторная установка и проверка — `sudo ./scripts/updater.sh install --yes` / `ensure` / `verify` (фактическое состояние: автозапуск, работа, перезапуск при сбоях, актуальность файла службы). Каждое обновление приводит файл службы к версии релиза, а помощник сам перезапускается на новом коде; интерфейс предупреждает, если помощник устарел (версия обмена) или служба установлена не полностью. Помощник выполняет только фиксированный набор действий в чистом окружении (пробрасываются лишь настройки прокси и сертификатов).

Миграции относятся только к внутренней базе KAV Checker; базы KSC не затрагиваются. Данные пользователей, отчёты и настройки при обновлении не удаляются. Очистка касается только образов этого проекта, чужие образы и тома не трогаются.

### Зеркала npm и pip (локальная сборка)

Если с сервера недоступен registry.npmjs.org или pypi.org, укажите зеркала в `.env`:

```bash
NPM_REGISTRY=https://npm-mirror.gitverse.ru
PIP_INDEX_URL=https://<зеркало pypi>/simple
```

Если зеркало уже настроено на сервере (`npm config`, `~/.npmrc` владельца репозитория, `pip.conf`, переменные окружения), а в `.env` его нет, при сборке оно находится и **сохраняется в `.env`** (в журнале — строка «зеркало найдено в настройках сервера»), так что Docker его не игнорирует; настройки сохраняются при обновлениях. Адреса передаются в сборку образов, файлы проекта не меняются, контрольные суммы пакетов из `package-lock.json` проверяются как обычно; кэш npm сохраняется между сборками. Docker Hub (базовые образы `node`, `python`, `nginx`) зеркалом npm/pip не заменяется: при его недоступности используйте готовые образы или настройте `registry-mirrors` в `/etc/docker/daemon.json`.

### Проверка отказоустойчивости

`tests/updater/run.sh` — сценарии на подставном docker: успешное обновление из готовых образов (при `IMAGE_REPO=kavcheck`, без сборки), недоступные ghcr.io и Docker Hub, отсутствующие образы, обрыв сети, зависшие загрузка, сборка и миграция, ошибка миграции и проверки здоровья, `kill -9` во время миграции и в других этапах (имитация перезагрузки), остановка помощника и его перезапуск, параллельный запуск. После каждого сбоя проверяется: работает прежняя версия и данные, нет оставшихся процессов, блокировка снята, причина записана в отчёте. Тесты выполняются в CI.

## Откат

Администрирование → Обновления → «Откатить версию» или `./scripts/rollback.sh`. Код и образы возвращаются к предыдущей версии без пересборки. Если новая версия изменила схему внутренней базы, откат останавливается: сначала восстановите резервную копию, снятую перед обновлением (метка `pre-<прежняя версия>`), затем повторите откат.

## Резервные копии

```bash
./scripts/backup.sh [--label имя] [--keep 14]
```

Создаёт `DATA_ROOT/backups/<проект>-db-<время>[-метка].dump` (pg_dump, custom format) и копию `.env` (содержит секреты, права 600). Хранятся последние 14. Кнопка «Создать резервную копию» в разделе «Обновления» делает то же через помощника. Перед каждым обновлением и восстановлением копия создаётся автоматически.

Рекомендуется копировать каталог `DATA_ROOT/backups` и `.env` на внешний носитель. `DATA_ROOT/reports` — файлы отчётов (можно восстановить повтором отчёта).

## Восстановление

В браузере: Администрирование → Обновления → «Резервные копии» → «Восстановить» у нужной копии, подтверждение словом «ВОССТАНОВИТЬ». На сервере:

```bash
./scripts/restore.sh DATA_ROOT/backups/<проект>-db-<время>.dump
```

Порядок: копия текущей базы (метка `pre-restore`) → остановка backend и worker → текущая база переименовывается в `<база>_before_restore_<время>` → копия восстанавливается в новую пустую базу → запуск. При ошибке прежняя база возвращается на место. Хранятся две последние отложенные базы каждого вида. Восстановление возвращает пользователей, настройки, источники, проверки и сведения об отчётах к моменту копии; сессии, открытые после копии, закрываются.

На новом сервере: установить ту же версию (`git checkout vX.Y.Z`, `scripts/install.sh`), положить сохранённый `.env` (с тем же `APP_MASTER_KEY` — иначе пароли источников и LDAP и второй фактор пользователей придётся настроить заново), восстановить базу.

## Выпуск новой версии (для сопровождающих)

```bash
./scripts/release.sh check      # VERSION, CHANGELOG, package.json согласованы
./scripts/release.sh patch      # или minor: поднимает версию, раздел CHANGELOG, коммит и тег
git push origin main --tags     # CI собирает и публикует образы и страницу релиза
```

Публикация происходит только после явного push тега. Для отдельного репозитория организации достаточно задать `GITHUB_REPO` и `IMAGE_REPO` в `.env` установок.
