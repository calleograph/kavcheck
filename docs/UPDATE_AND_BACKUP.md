# Обновление, откат, резервное копирование

## Как устроено

Релизы публикуются в GitHub: тег `vX.Y.Z`, страница релиза с описанием из CHANGELOG и образы `ghcr.io/<владелец>/kavcheck-backend:vX.Y.Z`, `…-web:vX.Y.Z`. Все установки обновляются из одного источника релизов, сохраняя свои `.env`, внутреннюю базу, отчёты и подключения.

Контейнер backend не имеет доступа к Docker и git сервера. Обновление из браузера выполняет **помощник** — служба systemd `kavcheck-updater-<проект>` на сервере (`scripts/updater.sh`), которая читает запросы из каталога `DATA_ROOT/updater` и выполняет только фиксированный набор действий: проверка релизов, обновление, откат, резервная копия. Произвольные команды из веб-интерфейса выполнить нельзя.

## Обновление

В браузере: Администрирование → Обновления → «Проверить релизы» → «Обновить». Ход выполнения показывается построчно, итог — в истории.

На сервере:

```bash
./scripts/update.sh            # до последнего релиза
./scripts/update.sh --to v0.2.0
./scripts/update.sh --build    # собрать образы локально (нет доступа к реестру образов)
```

Шаги `scripts/update.sh`: fetch тегов → checkout релиза → образы (pull или сборка) → резервная копия внутренней базы и `.env` → остановка backend/worker → миграции Alembic → запуск → ожидание healthcheck → проверка `/api/v1/health/ready` и версии → удаление старых образов проекта (остаются текущая и предыдущая версии). При сбое до перезапуска код возвращается на прежнюю версию; при сбое после перезапуска выполняется `rollback.sh`.

Миграции относятся только к внутренней базе KAV Checker; базы KSC не затрагиваются. Данные пользователей, отчёты и настройки при обновлении не удаляются. Очистка касается только образов этого проекта (по имени `IMAGE_REPO-*`), чужие образы и тома не трогаются.

## Откат

Администрирование → Обновления → «Откатить на предыдущую версию» или `./scripts/rollback.sh`. Код и образы возвращаются к предыдущей версии без пересборки. Если новая версия изменила схему внутренней базы, откат останавливается: сначала восстановите резервную копию, снятую перед обновлением (`scripts/restore.sh <файл>`), затем повторите откат.

## Резервные копии

```bash
./scripts/backup.sh [--label имя] [--keep 14]
```

Создаёт `DATA_ROOT/backups/<проект>-db-<время>.dump` (pg_dump, custom format) и копию `.env` (содержит секреты, права 600). Хранятся последние 14. Кнопка «Создать резервную копию» в разделе «Обновления» делает то же через помощника. Перед каждым обновлением копия создаётся автоматически.

Рекомендуется копировать каталог `DATA_ROOT/backups` и `.env` на внешний носитель. `DATA_ROOT/reports` — файлы отчётов (можно восстановить повтором отчёта).

## Восстановление

```bash
./scripts/restore.sh DATA_ROOT/backups/<проект>-db-<время>.dump
```

Останавливает backend и worker, восстанавливает базу (`pg_restore --clean`), запускает сервисы. На новом сервере: установить ту же версию (`git checkout vX.Y.Z`, `scripts/install.sh`), положить сохранённый `.env` (с тем же `APP_MASTER_KEY` — иначе пароли источников и LDAP придётся ввести заново), восстановить базу.

## Выпуск новой версии (для сопровождающих)

```bash
./scripts/release.sh check      # VERSION, CHANGELOG, package.json согласованы
./scripts/release.sh patch      # или minor: поднимает версию, раздел CHANGELOG, коммит и тег
git push origin main --tags     # CI собирает и публикует образы и страницу релиза
```

Публикация происходит только после явного push тега. Для отдельного репозитория организации достаточно задать `GITHUB_REPO` и `IMAGE_REPO` в `.env` установок.
